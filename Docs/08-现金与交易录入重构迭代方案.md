## 2. 背景与现状核对

### 2.1 快照体系

InvestRing 有三张快照表，只增不改：

- `portfolio_position`：持仓快照（每支基金的 shares / 各平台 CASH amount）
- `portfolio_value_snapshot`：组合市值快照
- `investor_holding`：投资人份额快照

生成顺序固定：`portfolio_position` → `portfolio_value_snapshot` → `investor_holding`。

**现状：** 快照生成函数 `recalculate_snapshots`（`snapshot_service.py` 函数 `recalculate_snapshots`，调查时行号 127+）按天循环，每调 `_generate_portfolio_position` 生成单日持仓快照。快照数据是后续所有披露/收益的**唯一真相源**。

### 2.2 三类输入源

快照生成从三类数据源读取：

| 输入源 | 表 | 应用日字段 | 纳入条件 |
|---|---|---|---|
| 申赎 | `subscription` | `confirm_date` | `status=='confirmed' AND confirm_date <= target_date` |
| 调仓交易 | `trade` | `confirm_date` | `status=='confirmed' AND confirm_date <= target_date` |
| 份额变动事件 | `share_change_event` | `ex_date`（除息/除权日） | **当前仅 warning，未实际应用**（见第 9 节） |

### 2.3 现状核对要点

| 项目 | 现状 |
|---|---|
| 快照表是否可手动改写 | `update_cash_position`（`positions.py` 函数 `update_cash_position`）直接 upsert `portfolio_position.amount`——**违反"系统生成唯一真相源"原则** |
| Trade 是否被快照删除级联 | **否**——`_cascade_unconfirm_subscriptions` 仅处理 Subscription |
| 手动市值记录表 | **不存在**——无法记录"手动更新现金市值"而不污染 trade 流水语义 |
| 份额变动事件是否在快照中应用 | **否**——`_check_share_change_events` 仅 warning，无 `shares_change`/`cash_change` 写入路径 |
| 快照硬闸门对 QDII 是否正确 | **否**——用 `trade_date < target` 而非 `confirm_date <= target`，T+2 的 QDII 被误杀（详见第 10 节） |
| Trade 确认有无自动链路 | **否**——`auto_confirm_after_snapshot` 仅处理 Subscription |

## 3. 核心设计原则

### 3.1 快照表 = 唯一真相源

**规则：** 三张快照表只由系统生成（`recalculate_snapshots`），**禁止任何路径手动改写**。所有对外披露的市值与收益只读快照表。

**含义：** 修正数据的唯一途径是重新生成快照。实时计算函数（如 `calculate_available_cash`）仅作预览，不作为披露/收益真相。`update_cash_position` 改道写 `manual_market_value` 表（见第 5 节）。

### 3.2 Trade 不可变 / 申赎依赖快照级联

**规则：**

- **Trade（调仓/交易）= 客观交易记录。** 其净值数据来自 `price_record` 表（数据源为基金公司/证券公司等权威机构，一般不变更）。历史交易状态、确认信息**不会因快照改变而改变**。删快照不级联改 Trade。
- **Subscription（申赎）= 取值依赖前一日快照 NAV。** 本系统是记账系统，非严格规范交易系统，记账有疏漏须重跑数据。故删快照时依赖该日 NAV 确认的申赎须级联回退 pending，待重算后重新确认。

**代码确认：** `_cascade_unconfirm_subscriptions`（`snapshot_service.py` 函数 `_cascade_unconfirm_subscriptions`，调查时行号 309-352）仅查 `Subscription`（`apply_date == snapshot_date AND status == 'confirmed'`）并退 pending，全文件无 Trade 级联逻辑。

### 3.3 手动市值层（manual_market_value 表）

**规则：** 手动维护的非净值资产（现金等）市值存入新的 `manual_market_value` 表。快照生成时按日期读取覆盖。**不走 trade 表**（不污染"trade=流水"语义），**不进现金流集合**（待绩效评价体系定义口径后统一纳入）。详见第 5 节。

### 3.4 事件走快照主链、不污染 manual_market_value

**规则：** 份额变动事件（ShareChangeEvent）改的是成分基金份额/现金持仓（进 `portfolio_position`），属快照系统生成内容，走快照主链路；`manual_market_value` 仅服务非净值资产市值。二者独立。详见第 9 节。

## 4. 交易录入规范

### 适用范围

以下 5 条规范适用于 **Trade（调仓交易）、Subscription（申购赎回）、ShareChangeEvent（份额变动事件）** 三类交易的录入与快照生成。三类有不同的日期字段和确认规则，规范中的条件需按类型区分。

### 三类交易日期字段对照

| 字段角色 | Trade | Subscription | ShareChangeEvent |
|---|---|---|---|
| 申请日 | `trade_date` | `apply_date` | —（无独立申请日） |
| 基数锚（确认时读快照基数） | —（隐式，trade_date 当日快照） | —（隐式，apply_date 当日 NAV） | **`entitlement_date`**（登记日快照份额） |
| 应用日（纳入快照） | `confirm_date` | `confirm_date` | **`ex_date`**（除息/除权日） |

**关键区别：** 事件的"申请"和"应用"没有分离出两个独立日期字段——`ex_date` 既表示"应用日"（↔ confirm_date），`entitlement_date` 是事件独有的"基数锚"（登记日持仓快照的份额）。Trade/Subscription 没有独立的基数锚字段（隐含在各自的 trade_date / apply_date 当日快照中）。

### 三类适用矩阵

| 规范 | Trade | Subscription | ShareChangeEvent |
|---|---|---|---|
| 1 日期齐备 | `trade_date` + `confirm_date` | `apply_date` + `confirm_date` | `ex_date` + `entitlement_date`（无独立 confirm_date） |
| 2 确认日规则 | 按产品 `confirm_days` | 固定 T+1 | **不适用**——确认靠快照存在性，非 T+N 推算 |
| 3 仅可录入 D+1 | `trade_date > D` | `apply_date > D` | **`ex_date > D`**（应用日不能落已生成快照中） |
| 4 补录删其后快照 | 闸门卡死风险（需先修闸门） | 级联回退 ✓ | 级联回退（需新增，双日期） |
| 5 D+1 处理完 | `confirm_date == D+1` | `confirm_date == D+1` | **`ex_date <= D+1` 仍 pending → 拦快照** |

### ShareChangeEvent 字段规则

**必填与约束（基于 `models/share_change_event.py` 实际字段 + 业务推理）：**

1. **外键完整性：** `portfolio_code` 必须存在；(`product_code`, `market`) 联合必须存在于 `product` 表（模型已有 `ForeignKeyConstraint`）
2. **交易日期约束：**
   - `ex_date` 和 `entitlement_date` 都必须为交易日（当前代码仅校验 `entitlement_date`，`share_change_events.py` 第 55 行）
   - **建议加约束：** `ex_date >= entitlement_date`（除息/除权日不早于登记日——拆分/合并/送股通常同日，现金分红除息日通常晚 1 个交易日）
3. **event_type 决定子字段必填：**
   - `cash_dividend` → `div_cash` 必填
   - `reinvest_dividend` → `div_cash` + `reinvest_nav` 必填
   - `share_split` / `share_merge` / `bonus_share` → `ratio` 必填
   - `forced_adjustment` → `shares_change` / `cash_change` 至少其一必填
4. **状态流转：** `pending` → `confirmed`（条件：`entitlement_date` 持仓快照存在 → `MISSING_POSITION_SNAPSHOT`）→ `cancelled`（仅 pending 可取消）。`confirmed` 不可回退 pending（除非走快照级联删除，见第 9 节）
5. **`entitlement_shares` 应强制自动填入：** 确认时从 `entitlement_date` 的 `portfolio_position.shares` 自动读取并写入，不接受调用方传来的值

### 规范 1：日期字段齐备

**规则：** 交易录入时所有日期字段都应存在（非留空后补）。

- Trade：`trade_date` + `confirm_date` 齐备
- Subscription：`apply_date` + `confirm_date` 齐备
- ShareChangeEvent：`ex_date` + `entitlement_date` 齐备（事件无独立 confirm_date，确认时置 `confirmed_at` 时间戳并通过快照存在性校验）

**验收点：** 录入层（前端/导入）按类型校验日期非空。

### 规范 2：确认日规则（T+1 与 confirm_days）

**适用：** Trade、Subscription。ShareChangeEvent **不适用**——事件的"确认"条件是 `entitlement_date` 持仓快照存在，非 T+N 推算。

**规则：**

- 组合申购、组合赎回：**T+1 确认**（`apply_date` 的下一交易日为 `confirm_date`）
- 组合内部调仓：确认日期由**产品表 `confirm_days`** 字段确定（`trade_date + confirm_days` 个交易日）

**代码确认：**

- `subscription_service.confirm_single_subscription`：confirm_date = apply_date 下一交易日
- `Product.confirm_days`（`schemas/product.py`）：默认 1，按 market/is_qdii 自动计算
- `trades.py` 函数 `confirm_trade`（调查时行号 485-487）：调仓 confirm_date = `_get_next_trading_day(trade_date, days=product.confirm_days)`

**含义：** 场内基金 confirm_days=0（当天），场外 CN_OTC=1（T+1），QDII=2（T+2）。补录历史交易须按产品 confirm_days 反推 confirm_date，不能一律 T+1。

### 规范 3：仅可录入 D+1 日及之后的交易

**规则：** 正常录入只允许后续日期的交易。快照已到 D，新交易的"应用日"不能落在已生成快照上。

- Trade：`trade_date > D`
- Subscription：`apply_date > D`
- ShareChangeEvent：**`ex_date > D`**（应用日不能 ≤ D，`entitlement_date` 可 ≤ D——只要那天快照已存在、基数可读）

**验收点：** 录入层按类型拦截。

### 规范 4：补录 D-N 日交易须先删其后快照

**规则：** 录入应用日 ≤ D 的交易（D-N），必须先**删除 D-N 之后全部快照** → 补录 → 重生成快照链。

**代码支撑：** `subscriptions.py`（调查时行号 301-321）已实现快照依赖保护：已 confirmed 且 `confirm_date` 及之后有快照的申赎，拒绝 unconfirm（error: `SNAPSHOT_DEPENDENCY`），提示"请先删除 confirm_date 及之后快照"。

**三类落实：**

- Subscription：删快照 → `_cascade_unconfirm_subscriptions` 退 pending（已有）→ regen 自愈
- Trade：删快照 → 无级联（Trade 不可变）→ regen 自动确认（需新增，见 §13 任务 2）
- ShareChangeEvent：删快照 → **双日期级联回退**（需新增 `_cascade_unconfirm_share_change_events`，见 §9.2.3）→ regen 重新应用

**⚠ 前置依赖：** 本规范依赖快照硬闸门修复（第 10 节）——否则 QDII/跨天组合 regen 会被闸门假阳性卡死。regen 链须覆盖到最新日。regen 前组合内不得有"已过期仍 pending"的交易。

### 规范 5：D+1 快照须处理完当日应应用交易

**规则：** 生成 D+1 快照前，必须处理完所有"应用日 = D+1 或更早"的交易，否则它们会被过滤遗漏。

- Trade / Subscription：`confirm_date == D+1` 仍 pending → 拦快照
- ShareChangeEvent：**`ex_date <= D+1` 仍 pending → 拦快照**（应用日已到却未确认、未纳入快照）

**⚠ 边界：** `_check_pending_transactions` 仅拦截 `apply_date < target_date` 的 pending，对 `apply_date == target_date` 的 pending **不拦截**。规范 5 是业务前置要求，非闸门自动保证。推荐定时任务按序执行：自动确认当日到期交易 → 校验无遗留 pending → 生成快照。

## 5. 手动市值层（manual_market_value 表）

### 5.1 定位与命名

**命名：** `manual_market_value`（手动市值表）。`manual` = 人工输入来源，`market_value` = 市值语义，与 `price_record`（外部权威自动同步价格）形成对称。

以下文档中凡写 `override` / `override 表` / `非净值资产市值覆盖层` 的，均指此表。

### 5.2 设计

**新增表** `manual_market_value`，手动维护的现金等非净值资产市值存入此表。快照生成时按 `(portfolio, platform, product, date)` 读取：有记录则取覆盖值，无则按原隐式计算。

**覆盖行为：绝对替换**（不是叠加），避免"隐式算出 100 + 手动市值 101 = 201"的双计。快照为增量基线，T 日现金被覆盖值钉成 V 后，T+1 从 V 接着流。

**Schema 需求：** 至少含字段 `portfolio_code`、`platform_code`、`product_code`、`date`、`market_value`，以及审计字段 `computed_value`（隐式计算值）、`created_by`、`created_at`、`updated_at`。`(portfolio_code, platform_code, product_code, date)` 唯一约束，upsert 语义。如需追溯修改轨迹应版本化。

**与份额变动事件的关系：** 事件（ShareChangeEvent）改的是成分基金份额/现金持仓，属快照系统生成内容，走快照主链、不污染 `manual_market_value`；`manual_market_value` 仅服务非净值资产市值。详见第 9 节。

### 5.3 否决方案记录

- **adjust-trade（trade 表记 CASH adjust 类型）：** 否决——重估伪装成流水污染 trade 语义
- **基金调仓买卖纳入现金现金流：** 否决——属组合内部资产转换

## 6. 共享隐式流函数与 get_cash_value

### 6.1 compute_implicit_flow（新抽象）

抽取共享纯函数：

```python
def compute_implicit_flow(
    db: Session,
    portfolio_code: str,
    platform_code: str | None = None,
    as_of_date: date
) -> Decimal:
```

**行为：**

- `baseline_date` = 最新 CASH snapshot_date ≤ `as_of_date`（未指定 platform 时按平台分别取各自基线）
- 流区间：`(baseline_date, as_of_date]`——严格大于基线、含目标日当天
- 申赎：`confirm_date` 在区间内的 confirmed
- 调仓买卖：`confirm_date` 在区间内的 confirmed（CASH 跨平台转移纳入，基金内部买卖纳入）
- pending 买入：按 **`apply_date <= as_of_date`** 过滤（⚠ 不是全部 pending——当前 `calculate_available_cash` 减全部 pending 买入对"now"合理，但参数化后必须按日期过滤，否则 T 日之后才发起的 pending 会提前扣 T 日现金）

**替换：** `calculate_available_cash` 旧函数删除，所有调用点改调以下二者之一。

### 6.2 get_cash_value（快照生成用）

```python
def get_cash_value(db, portfolio_code, platform_code, date):
    v = compute_implicit_flow(db, portfolio_code, platform_code, date)
    manual = read_manual_market_value(db, portfolio_code, platform_code, "CASH", date)
    if manual is not None:
        v = manual.market_value  # 绝对替换
    return v
```

- **实时预览：** 调 `compute_implicit_flow(today)`，**不读** `manual_market_value`
- **快照生成：** 调 `get_cash_value(date)`，读 `manual_market_value` 覆盖后落库

### 6.3 实时预览 vs 快照真相（D 日窗口）

D 日快照未生成、`manual_market_value` 已有 D 日市值时：实时 `compute_implicit_flow(D)` 算出隐式流预览值（不含人工重估）。D 日快照生成后 `get_cash_value(D)` 读 `manual_market_value` → 落库。实时与快照存在一个快照生成时点的窗口差——这是接受的估值系统常态：实时预览，披露以快照为准。

**前端约束：** 不得把实时预览当正式披露数字展示。

## 7. 现金转移设计

### 7.1 数据结构

复用 `Trade` 表，一次转移生成**两条 CASH 交易记录**，通过 `transfer_group` 字段关联：

- 卖出腿：`platform_code=from_platform`、`trade_type="sell"`、`product_code="CASH"`，减转出平台现金
- 买入腿：`platform_code=to_platform`、`trade_type="buy"`、`product_code="CASH"`，增转入平台现金
- 两条均 `price=1`、`actual_amount=amount`（现金面值，无价格/份额换算）

### 7.2 当天 vs 跨天

由请求体 `cross_day` 布尔字段决定（`CashTransferCreate.cross_day: bool = False`，`schemas/cash_transfer.py`，调查时行号 11），**默认当天完成**。

| | `cross_day=False`（当天） | `cross_day=True`（跨天/T+1） |
|---|---|---|
| 卖出腿 | 立即 confirmed，confirm_date=transfer_date | 立即 confirmed，confirm_date=transfer_date |
| 买入腿 | 立即 confirmed，confirm_date=transfer_date | **pending，confirm_date=None** |
| 现金效果 | 当天转出减少、转入增加 | 转出日减少，**次日**才增加 |
| 在途资金 | 无 | 在途期间不计入任何平台可用现金 |

### 7.3 跨天买入腿确认

靠专属端点 `confirm_cash_transfer`（`cash_transfers.py` 函数 `confirm_cash_transfer`，调查时行号 193-249），**非快照自动确认**：

- `confirm_date = _get_next_trading_day(buy_trade.trade_date)`（硬编码 T+1，与产品 `confirm_days` 无关）
- 守卫：`if confirm_date > date.today():` → `TRANSFER_NOT_READY`（228-236）
- 到日才置 confirmed 并写入 confirm_date

### 7.4 confirm_date=None 的语义

跨天买入腿创建时 `confirm_date=None`。与"创建时钉死 D+1"的本质区别：

| 维度 | `None`（现状，正确） | 钉 D+1 |
|---|---|---|
| 日期来源 | 确认端点当场派生 | 创建期输入 |
| 对快照可见性 | 不可见（None 排除），确认前不进快照 | 可见（预期 D+1 确认） |
| 抗漂移 | 强（延迟确认自动用正确日） | 弱（钉死后若延迟则为错误值） |
| 语义诚实度 | 高："尚未排期" | 低：明明没排期却写了日期 |

**结论：** 保持 `None`。由此推论：快照硬闸门修复（第 10 节）必须保留 `confirm_date is None` 回退分支。

## 8. Trade 确认流程

### 8.1 写入即 pending → 二次确认

**用户写入一笔交易后，必须再做一次确认真交易才生效（变为 confirmed）。**

**代码事实：**

1. `create_trade`（`trades.py`，调查时行号 331-445）：无论买入（398 行）卖出（436 行），新建 Trade 一律 `status="pending"`
2. `confirm_trade`（调查时行号 460-467）：仅 `status=="pending"` 可确认；未传 `confirm_date` 时按 `product.confirm_days` 推下一交易日
3. 确认时可传 `confirm_date`（覆盖自动推算，适合补录）和 `price`（手动指定净值）
4. 净值型产品（OEF/LOF + CN_OTC）确认走 `_get_nav_for_trade_confirmation`：QDII T 日净值缺失 → `MISSING_QDII_NAV` 拒绝确认（禁止向前查找）

### 8.2 Trade 确认无自动链路（与申购不同）

| 交易类型 | 自动确认？ |
|---|---|
| 申购/赎回 Subscription | **有**——快照后 `auto_confirm_after_snapshot` 自动重确认 |
| 普通基金调仓 Trade | **无**——须人工/外部定时任务显式调 `confirm_trade` |
| 现金转移（当天） | 创建即确认（内联） |
| 现金转移（跨天）买入腿 | **无**——须显式调 `confirm_cash_transfer` |

**⚠ `auto_confirm_after_snapshot`（`snapshot_service.py` 函数 `auto_confirm_after_snapshot`，调查时行号 838-916）的 `pending_subs` 只查 Subscription 表，Trade 不在其中。** 这是删快照→regen 场景 B/C 卡死的根因（第 11 节）。

### 8.3 两个确认端点不可混用

- `confirm_trade`（`trades.py`）：按 confirm_days 推日期 + 取净值算份额
- `confirm_cash_transfer`（`cash_transfers.py`）：下一交易日 + `TRANSFER_NOT_READY` 守卫 + 无净值

扩展自动确认时必须分别适配。

## 9. 份额变动事件（ShareChangeEvent）

### 9.1 现状

`ShareChangeEvent` 是独立事件表（`models/share_change_event.py`），`event_type` 含 cash_dividend / reinvest_dividend / share_split / share_merge / bonus_share / forced_adjustment，状态 pending→confirmed。**⚠ 当前数据库字段名为 `event_date`（需随本次迭代改名为 `ex_date`，含模型、router、Docs/02-03）。**

**`confirm_share_change_event`（`share_change_events.py` 函数 `confirm_share_change_event`，调查时行号 92-128）：**

- 仅置 `status="confirmed"`，**不应用 shares_change / cash_change 到快照**
- 校验权益登记日（`entitlement_date`）持仓快照存在（`MISSING_POSITION_SNAPSHOT`）

**`_check_share_change_events`（`snapshot_service.py` 函数 `_check_share_change_events`，调查时行号 1042-1060）：**

- 遇到 pending 事件**只返回 warning，不拦生成**
- 全代码**无任何把事件 shares_change / cash_change 写入 portfolio_position 的路径**

→ 事件语义（AGENTS §3.4 公式）目前"文档/模型里有、快照未落地"。

### 9.2 正确行为（应实现）

**事件是快照生成的第三类输入源**，与 Trade、Subscription 并列。

#### 9.2.1 事件在快照生成时"应用"，非"预警"

**应用日 = `ex_date`（除息/除权日）**，不是 `entitlement_date`（登记日）。生成 `target_date` 快照时，凡 `ex_date <= target_date` 且 `status == "confirmed"` 的事件，在 `_generate_portfolio_position` 中按公式改写成分基金份额 / 组合现金：

| event_type | 份额变化 | 现金变化 | 公式 |
|---|---|---|---|
| cash_dividend | 不变 | 增加 | cash_change = entitlement_shares × div_cash |
| reinvest_dividend | 增加 | 不变 | shares_change = entitlement_shares × div_cash / reinvest_nav |
| share_split | 增加 | 不变 | shares_after = entitlement_shares × ratio |
| share_merge | 减少 | 不变 | shares_after = entitlement_shares / ratio |
| bonus_share | 增加 | 不变 | shares_change = entitlement_shares × ratio |
| forced_adjustment | 指定 | 指定 | 直接填写 shares_change / cash_change |

pending 事件**不应用**，但应**拦截快照生成**（同 Trade 硬闸门，避免"漏应用"），而非仅 warning。

**`entitlement_shares` 取值：** 确认时从 `entitlement_date` 的 `portfolio_position.shares` 自动读取写入——这是事件独有的"基数锚"（登记日持仓份额）。Trade/Subscription 没有独立的基数锚字段（隐含在各自由 trade_date / apply_date 当日快照读取）。

#### 9.2.2 事件不影响实时口径

待确认事件不进实时可用现金/份额（与 Trade 冻结同构——pending 卖出既不实际扣份额，pending 事件也不实际改持仓）。

#### 9.2.3 双日期级联回退

事件依赖**两个日期**的快照，删快照时两层都需要级联：

**应用面向（`ex_date`）：** 除息/除权日快照被删 → 事件的应用在该日丢失 → 须回退。`ex_date == snapshot_date AND status == 'confirmed'` 的事件退 pending。

**基数面向（`entitlement_date`）：** 登记日快照被删 → 确认时读取的份额无处可读 → 须回退。`entitlement_date == snapshot_date AND status == 'confirmed'` 的事件退 pending。

新增函数 `_cascade_unconfirm_share_change_events(db, portfolio_code, snapshot_date)` 须**两个维度都查、按 OR 并集退 pending**，与 `_cascade_unconfirm_subscriptions` 同构。

#### 9.2.4 事件不进现金流集合

现金分红（fund→cash）和红利再投（fund shares↑）是资产内部形态转换，组合总视角钱没离开，不纳入现金流集合（待后续绩效评价体系定义口径）。`forced_adjustment` 若为外部真实注资/抽资才纳入。

#### 9.2.5 事件与 manual_market_value 独立

事件改成分基金份额/现金（进快照表），`manual_market_value` 改非净值资产市值。二者独立，事件走快照主链、不污染 `manual_market_value`。

## 10. 已知缺陷：QDII T+2 被闸门误杀

**严重程度：高。** 对持有 QDII（`confirm_days=2`）的组合，QDII 录入后到确认前的每一天快照都被拒。

### 10.1 问题机制

快照硬闸门 `_check_pending_transactions`（`snapshot_service.py` 函数 `_check_pending_transactions`，调查时行号 936-965）对 Trade 的判定：

```python
Trade.trade_date < target_date AND Trade.status == "pending"
```

QDII 调仓 D 日录入（`trade_date=D`），`confirm_date=D+2`。生成 D+1 快照（`target_date=D+1`）时：

- `trade_date=D < D+1` → True
- 状态 pending（合法，本就该 D+2 确认）
- → 闸门误判 → **拒绝生成 D+1 快照** ✗

但 D+1 快照本不该包含这笔 QDII（纳入条件 `confirm_date <= target_date`：D+2 > D+1，应排除）。→ **假阳性**。

**具体日期示例：** 假设 D = 2026-07-08（周三），QDII 调仓 trade_date=07-08，confirm_days=2 → confirm_date=07-10（周五）。生成 07-09（周四）快照时闸门误拒。

### 10.2 根因

用 `trade_date` 判断"该不该已确认"，但真正取决于 `confirm_date`。两者只在 T+1 时重合，QDII(T+2) 和场内(T+0) 均错位。

### 10.3 建议修复（非对称：Trade 侧换字段，Subscription 侧不动）

```python
from sqlalchemy import or_, and_

pending_trades = db.query(Trade).filter(
    Trade.portfolio_code == portfolio_code,
    Trade.status == "pending",
    or_(
        # 已知应确认日且已到期/过期
        and_(Trade.confirm_date.isnot(None), Trade.confirm_date <= target_date),
        # 未知（跨天买入腿 confirm_date=None）回退原逻辑
        and_(Trade.confirm_date.is_(None), Trade.trade_date < target_date),
    ),
).count()
```

Subscription 侧保持 `apply_date < target_date` 不变（其 pending 记录 confirm_date 为 None，且固定 T+1，`apply_date < target` 等价于"应已确认"）。

### 10.4 修复效果

| 交易类型 | 旧逻辑 | 修复后 |
|---|---|---|
| QDII T+2（D 录，D+2 确认），生成 D+1 | 误拒 ✗ | 放行 ✓（confirm_date=D+2 > D+1） |
| T+1 基金（D 录，D+1 确认），D+1 仍 pending | 拒（正确） | 拒（confirm_date=D+1 ≤ D+1） ✓ |
| 场内 T+0（D 录，D 确认），D+1 仍 pending | 拒（正确） | 拒 ✓ |
| 跨天现金买入腿（confirm_date=None），D+1 仍 pending | 拒（正确） | 拒（回退 trade_date<D） ✓ |

## 11. 删快照→重生成安全性分析

**前提：** 级联只碰 Subscription 和 ShareChangeEvent（有级联回退），不碰 Trade（无级联）。Trade 状态不因删快照改变。

### 场景分析

| 场景 | 结果 | 原因 |
|---|---|---|
| A：纯申赎组合（无跨天/QDII/事件） | **安全、自愈** | 删快照→申赎退 pending→regen 自动重确认→闭环 |
| B：有跨天现金买入腿 | **卡死** | 跨天腿 pending + trade_date < target → 闸门拦快照；regen 不自动确认该腿 |
| C：有 QDII T+2 在途 | **卡死** | QDII pending + trade_date < target → 闸门假阳性 + regen 不自动确认 |
| D：有 pending 事件 | **卡死（事件拦截实现后）** | 事件拦截快照后，含未确认事件的组合 regen 也会卡死 |

### 结论

卡死根因不是级联，而是 (1) 闸门用错字段误杀 + (2) regen 流程缺 Trade 侧自动确认 + (3) 事件侧自愈缺失。**闸门修复 + Trade 自愈 + 事件应用/级联三者必须一并纳入 regen 闭环，规范 4（补录删快照 regen）才在所有场景下成立。**

## 12. 独立任务：transfer_group 原子翻转

**问题：** 跨天现金转移的"卖出 CASH 已 confirm / 买入 CASH 仍 pending"两腿状态独立——confirm/unconfirm/cancel 一笔，另一笔不联动。可能造成"转出已扣、转入未到"的永久缺口。

**方案：** `transfer_group` 字段已存在，用数据库事务实现两腿原子翻转（confirm/unconfirm/cancel 任一腿，同 `transfer_group` 另一腿一起变）。

**独立性：** 本改造与 `manual_market_value` 层正交——即便未来把现金增减全显式化进 trade 表，原子翻转仍必要。
