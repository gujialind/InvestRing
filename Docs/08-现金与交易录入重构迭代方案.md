## 2. 背景与现状核对

### 2.1 快照体系

InvestRing 有三张快照表，只增不改：

- `portfolio_position`：持仓快照（每支基金的 shares / 各平台 CASH amount）
- `portfolio_value_snapshot`：组合市值快照
- `investor_holding`：投资人份额快照

生成顺序固定：`portfolio_position` → `portfolio_value_snapshot` → `investor_holding`。

**现状：** 快照生成函数 `recalculate_snapshots`（`snapshot_service.py` 函数 `recalculate_snapshots`，调查时行号 127+）按天循环，每调 `_generate_portfolio_position` 生成单日持仓快照。快照数据是后续所有披露/收益的**唯一真相源**。

### 2.2 三类输入源

快照生成从三类数据源读取：

| 输入源 | 表 | 确认日字段 | 纳入条件 |
|---|---|---|---|
| 申赎 | `subscription` | `confirm_date` | `status=='confirmed' AND confirm_date <= target_date` |
| 调仓交易 | `trade` | `confirm_date` | `status=='confirmed' AND confirm_date <= target_date` |
| 份额变动事件 | `share_change_event` | `entitlement_date` | **当前仅 warning，未实际应用**（见第 10 节） |

### 2.3 现状核对要点

| 项目 | 现状 |
|---|---|
| 快照表是否可手动改写 | `update_cash_position`（`positions.py` 函数 `update_cash_position`）直接 upsert `portfolio_position.amount`——**违反"系统生成唯一真相源"原则** |
| Trade 是否被快照删除级联 | **否**——`_cascade_unconfirm_subscriptions` 仅处理 Subscription |
| 非净值资产市值覆盖层 | **不存在**——无法记录"手动更新现金市值"而不污染 trade 流水语义 |
| 份额变动事件是否在快照中应用 | **否**——`_check_share_change_events` 仅 warning，无 `shares_change`/`cash_change` 写入路径 |
| 快照硬闸门对 QDII 是否正确 | **否**——用 `trade_date < target` 而非 `confirm_date <= target`，T+2 的 QDII 被误杀（详见第 11 节） |
| Trade 确认有无自动链路 | **否**——`auto_confirm_after_snapshot` 仅处理 Subscription |

## 3. 核心设计原则

### 3.1 快照表 = 唯一真相源

**规则：** 三张快照表只由系统生成（`recalculate_snapshots`），**禁止任何路径手动改写**。所有对外披露的市值与收益只读快照表。

**含义：** 修正数据的唯一途径是重新生成快照。实时计算函数（如 `calculate_available_cash`）仅作预览，不作为披露/收益真相。`update_cash_position` 改道写 override 表（见第 5 节）。

### 3.2 Trade 不可变 / 申赎依赖快照级联

**规则：**

- **Trade（调仓/交易）= 客观交易记录。** 其净值数据来自 `price_record` 表（数据源为基金公司/证券公司等权威机构，一般不变更）。历史交易状态、确认信息**不会因快照改变而改变**。删快照不级联改 Trade。
- **Subscription（申赎）= 取值依赖前一日快照 NAV。** 本系统是记账系统，非严格规范交易系统，记账有疏漏须重跑数据。故删快照时依赖该日 NAV 确认的申赎须级联回退 pending，待重算后重新确认。

**代码确认：** `_cascade_unconfirm_subscriptions`（`snapshot_service.py` 函数 `_cascade_unconfirm_subscriptions`，调查时行号 309-352）仅查 `Subscription`（`apply_date == snapshot_date AND status == 'confirmed'`）并退 pending，全文件无 Trade 级联逻辑。

### 3.3 非净值资产 override 覆盖层

**规则：** 手动维护的非净值资产（现金等）市值存入 **新的 override 表**（非净值资产市值记录表），快照生成时按日期读取覆盖。**覆盖不走 trade 表**（不污染"trade=流水"语义），**不进现金流集合 F_t**（不扭曲现金收益率计算）。详见第 5 节。

### 3.4 事件走快照主链、不污染 override

**规则：** 份额变动事件（ShareChangeEvent）改的是成分基金份额/现金持仓（进 `portfolio_position`），属快照系统生成内容，走快照主链路；override 仅服务非净值资产市值。二者独立。详见第 10 节。

## 4. 交易录入规范

全系统以"已生成的最新快照日 D"为时间锚点（D = `MAX(snapshot_date)` of `portfolio_value_snapshot`）。

### 规范 1：apply_date 与 confirm_date 双日期齐备

**规则：** 交易录入时 `apply_date` 与 `confirmed_date` 都应存在（非留空后补）。

**现状：** Schema 允许 Optional，逻辑依赖非空但录入层无强制校验。

**验收点：** 录入层（前端/导入）校验双日期非空。

### 规范 2：确认日规则（T+1 与 confirm_days）

**规则：**

- 组合申购、组合赎回：**T+1 确认**（`apply_date` 的下一交易日为 `confirm_date`）
- 组合内部调仓：确认日期由**产品表 `confirm_days`** 字段确定（`trade_date + confirm_days` 个交易日）

**代码确认：**

- `subscription_service.confirm_single_subscription`：confirm_date = apply_date 下一交易日
- `Product.confirm_days`（`schemas/product.py`）：默认 1，按 market/is_qdii 自动计算
- `trades.py` 函数 `confirm_trade`（调查时行号 485-487）：调仓 confirm_date = `_get_next_trading_day(trade_date, days=product.confirm_days)`

**含义：** 场内基金 confirm_days=0（当天），场外 CN_OTC=1（T+1），QDII=2（T+2）。补录历史交易须按产品 confirm_days 反推 confirm_date，不能一律 T+1。

### 规范 3：仅可录入 D+1 日的交易

**规则：** 正常录入只允许 `apply_date = D+1`。快照已到 D，新交易只能发生在 D 之后。

**验收点：** 录入层拦截 `apply_date <= D`。

### 规范 4：补录 D-N 日交易须先删其后快照

**规则：** 录入 D 及之前的交易（D-N），必须先**删除 D-N 之后全部快照**，再补录，最后重生成快照链。

**代码支撑：** `subscriptions.py`（调查时行号 301-321）已实现快照依赖保护：已 confirmed 且 `confirm_date` 及之后有快照的申赎，拒绝 unconfirm（error: `SNAPSHOT_DEPENDENCY`），提示"请先删除 confirm_date 及之后快照"。

**⚠ 前置依赖：** 本规范依赖快照硬闸门修复（第 11 节）——否则 QDII/跨天组合 regen 会被闸门假阳性卡死。regen 链须覆盖到最新日。regen 前组合内不得有"已过期仍 pending"的 Trade。

### 规范 5：D+1 快照须处理完当日确认交易

**规则：** 生成 D+1 快照前，必须处理完**所有 `confirmed_date = D+1` 的交易**（申购、赎回、调仓、现金转移），否则它们会被 `status=='confirmed'` 过滤遗漏。

**⚠ 边界：** `_check_pending_transactions` 仅拦截 `apply_date < target_date` 的 pending，对 `apply_date == target_date` 的 pending **不拦截**。所以规范 5 是业务前置要求，非闸门自动保证。推荐定时任务按序执行：自动确认 `apply_date==D+1` 的待确认交易 → 校验无遗留 pending → 生成快照。

## 5. 非净值资产市值覆盖层（override 表）

### 5.1 设计

**新增表**"非净值资产市值记录表"，手动维护的现金等非净值资产市值存入此表。快照生成时按 `(portfolio, platform, product, date)` 读取：有记录则取覆盖值，无则按原隐式计算。

**覆盖行为：绝对替换**（不是叠加），避免"隐式算出 100 + override 101 = 201"的双计。快照为增量基线，T 日现金被 override 钉成 V 后，T+1 从 V 接着流。

**Schema 需求：** 至少含字段 `portfolio_code`、`platform_code`、`product_code`、`date`、`override_value`，以及审计字段 `computed_value`（隐式计算值）、`created_by`、`created_at`、`updated_at`。`(portfolio_code, platform_code, product_code, date)` 唯一约束，upsert 语义。如需追溯修改轨迹应版本化。

**与份额变动事件的关系：** 事件（ShareChangeEvent）改的是成分基金份额/现金持仓，属快照系统生成内容，走快照主链、不污染 override；override 仅服务非净值资产市值。详见第 10 节。

### 5.2 否决方案记录

- **adjust-trade（trade 表记 CASH adjust 类型）：** 否决——重估伪装成流水污染 trade 语义，且算现金收益时需 special-case 过滤
- **基金调仓买卖纳入现金现金流：** 否决——属组合内部资产转换，纳入会扭曲"现金自身收益"残差

## 6. 共享隐式流函数与 get_cash_value

### 6.1 compute_implicit_flow（新抽象）

抽取共享纯函数：

```python
def compute_implicit_flow(
    db: Session,
    portfolio_code: str,
    platform_code: str | None = None,
    as_of_date: date
) -> Decimal:
```

**行为：**

- `baseline_date` = 最新 CASH snapshot_date ≤ `as_of_date`（未指定 platform 时按平台分别取各自基线）
- 流区间：`(baseline_date, as_of_date]`——严格大于基线、含目标日当天
- 申赎：`confirm_date` 在区间内的 confirmed
- 调仓买卖：`confirm_date` 在区间内的 confirmed（CASH 跨平台转移纳入，基金内部买卖纳入）
- pending 买入：按 **`apply_date <= as_of_date`** 过滤（⚠ 不是全部 pending——当前 `calculate_available_cash` 减全部 pending 买入对"now"合理，但参数化后必须按日期过滤，否则 T 日之后才发起的 pending 会提前扣 T 日现金）

**替换：** `calculate_available_cash` 旧函数删除，所有调用点改调以下二者之一。

### 6.2 get_cash_value（快照生成用）

```python
def get_cash_value(db, portfolio_code, platform_code, date):
    v = compute_implicit_flow(db, portfolio_code, platform_code, date)
    override = read_override(db, portfolio_code, platform_code, "CASH", date)
    if override is not None:
        v = override.value  # 绝对替换
    return v
```

- **实时预览：** 调 `compute_implicit_flow(today)`，**不读 override**
- **快照生成：** 调 `get_cash_value(date)`，读 override 覆盖后落库

### 6.3 实时预览 vs 快照真相（D 日窗口）

D 日快照未生成、override 已有 D 日市值时：实时 `compute_implicit_flow(D)` 算出隐式流预览值（不含人工重估）。D 日快照生成后 `get_cash_value(D)` 读 override → 落库。实时与快照存在一个快照生成时点的窗口差——这是接受的估值系统常态：实时预览，披露以快照为准。

**前端约束：** 不得把实时预览当正式披露数字展示。

## 7. 现金子账户 TWR 收益率

### 7.1 方法选择

用**时间加权收益（TWR）**，不套组合 IRR 的裸 IRR。

**理由：** 现金靠手动更新市值（amount 可含货基收益/利息，非恒定面值），有每日市值序列。TWR 不受申赎时序扭曲，最纯粹衡量现金管理能力。

### 7.2 公式

```
现金收益(段) = C_t − C_{t−1} − F_t
```

其中：

- `C_t`：t 日现金市值（从快照表读取）
- `F_t`：t 日真实现金流

### 7.3 现金流 F_t 口径

| 纳入 F_t | 不纳入 F_t |
|---|---|
| 申购（组合外部注资） | 基金调仓买卖（组合内部资产转换） |
| 赎回（组合外部抽资） | 现金分红、红利再投（资产形态转换） |
| 跨平台现金转移（transfer_group） | override 重估值（估值变动，非现金流） |

**含义：** override 重估不进 F_t，自动落入残差 = 现金自身收益（货基收益/利息）；基金调仓"现金→基金"不进 F_t，组合总视角钱没离开组合。

## 8. 现金转移设计

### 8.1 数据结构

复用 `Trade` 表，一次转移生成**两条 CASH 交易记录**，通过 `transfer_group` 字段关联：

- 卖出腿：`platform_code=from_platform`、`trade_type="sell"`、`product_code="CASH"`，减转出平台现金
- 买入腿：`platform_code=to_platform`、`trade_type="buy"`、`product_code="CASH"`，增转入平台现金
- 两条均 `price=1`、`actual_amount=amount`（现金面值，无价格/份额换算）

### 8.2 当天 vs 跨天

由请求体 `cross_day` 布尔字段决定（`CashTransferCreate.cross_day: bool = False`，`schemas/cash_transfer.py`，调查时行号 11），**默认当天完成**。

| | `cross_day=False`（当天） | `cross_day=True`（跨天/T+1） |
|---|---|---|
| 卖出腿 | 立即 confirmed，confirm_date=transfer_date | 立即 confirmed，confirm_date=transfer_date |
| 买入腿 | 立即 confirmed，confirm_date=transfer_date | **pending，confirm_date=None** |
| 现金效果 | 当天转出减少、转入增加 | 转出日减少，**次日**才增加 |
| 在途资金 | 无 | 在途期间不计入任何平台可用现金 |

### 8.3 跨天买入腿确认

靠专属端点 `confirm_cash_transfer`（`cash_transfers.py` 函数 `confirm_cash_transfer`，调查时行号 193-249），**非快照自动确认**：

- `confirm_date = _get_next_trading_day(buy_trade.trade_date)`（硬编码 T+1，与产品 `confirm_days` 无关）
- 守卫：`if confirm_date > date.today():` → `TRANSFER_NOT_READY`（228-236）
- 到日才置 confirmed 并写入 confirm_date

### 8.4 confirm_date=None 的语义

跨天买入腿创建时 `confirm_date=None`。与"创建时钉死 D+1"的本质区别：

| 维度 | `None`（现状，正确） | 钉 D+1 |
|---|---|---|
| 日期来源 | 确认端点当场派生 | 创建期输入 |
| 对快照可见性 | 不可见（None 排除），确认前不进快照 | 可见（预期 D+1 确认） |
| 抗漂移 | 强（延迟确认自动用正确日） | 弱（钉死后若延迟则为错误值） |
| 语义诚实度 | 高："尚未排期" | 低：明明没排期却写了日期 |

**结论：** 保持 `None`。由此推论：快照硬闸门修复（第 11 节）必须保留 `confirm_date is None` 回退分支。

## 9. Trade 确认流程

### 9.1 写入即 pending → 二次确认

**用户写入一笔交易后，必须再做一次确认真交易才生效（变为 confirmed）。**

**代码事实：**

1. `create_trade`（`trades.py`，调查时行号 331-445）：无论买入（398 行）卖出（436 行），新建 Trade 一律 `status="pending"`
2. `confirm_trade`（调查时行号 460-467）：仅 `status=="pending"` 可确认；未传 `confirm_date` 时按 `product.confirm_days` 推下一交易日
3. 确认时可传 `confirm_date`（覆盖自动推算，适合补录）和 `price`（手动指定净值）
4. 净值型产品（OEF/LOF + CN_OTC）确认走 `_get_nav_for_trade_confirmation`：QDII T 日净值缺失 → `MISSING_QDII_NAV` 拒绝确认（禁止向前查找）

### 9.2 Trade 确认无自动链路（与申购不同）

| 交易类型 | 自动确认？ |
|---|---|
| 申购/赎回 Subscription | **有**——快照后 `auto_confirm_after_snapshot` 自动重确认 |
| 普通基金调仓 Trade | **无**——须人工/外部定时任务显式调 `confirm_trade` |
| 现金转移（当天） | 创建即确认（内联） |
| 现金转移（跨天）买入腿 | **无**——须显式调 `confirm_cash_transfer` |

**⚠ `auto_confirm_after_snapshot`（`snapshot_service.py` 函数 `auto_confirm_after_snapshot`，调查时行号 838-916）的 `pending_subs` 只查 Subscription 表，Trade 不在其中。** 这是删快照→regen 场景 B/C 卡死的根因（第 12 节）。

### 9.3 两个确认端点不可混用

- `confirm_trade`（`trades.py`）：按 confirm_days 推日期 + 取净值算份额
- `confirm_cash_transfer`（`cash_transfers.py`）：下一交易日 + `TRANSFER_NOT_READY` 守卫 + 无净值

扩展自动确认时必须分别适配。

## 10. 份额变动事件（ShareChangeEvent）

### 10.1 现状

`ShareChangeEvent` 是独立事件表（`models/share_change_event.py`），`event_type` 含 cash_dividend / reinvest_dividend / share_split / share_merge / bonus_share / forced_adjustment，状态 pending→confirmed。

**`confirm_share_change_event`（`share_change_events.py` 函数 `confirm_share_change_event`，调查时行号 92-128）：**

- 仅置 `status="confirmed"`，**不应用 shares_change / cash_change 到快照**
- 校验权益登记日（`entitlement_date`）持仓快照存在（`MISSING_POSITION_SNAPSHOT`）

**`_check_share_change_events`（`snapshot_service.py` 函数 `_check_share_change_events`，调查时行号 1042-1060）：**

- 遇到 `entitlement_date <= target_date` 的 pending 事件**只返回 warning，不拦生成**
- 全代码**无任何把事件 shares_change / cash_change 写入 portfolio_position 的路径**

→ 事件语义（AGENTS §3.4 公式）目前"文档/模型里有、快照未落地"。

### 10.2 正确行为（应实现）

**事件是快照生成的第三类输入源**，与 Trade、Subscription 并列。

#### 10.2.1 事件在快照生成时"应用"，非"预警"

生成 `target_date` 快照时，凡 `entitlement_date <= target_date` 且 `status == "confirmed"` 的事件，在 `_generate_portfolio_position` 中按公式改写成分基金份额 / 组合现金：

| event_type | 份额变化 | 现金变化 | 公式 |
|---|---|---|---|
| cash_dividend | 不变 | 增加 | cash_change = entitlement_shares × div_cash |
| reinvest_dividend | 增加 | 不变 | shares_change = entitlement_shares × div_cash / reinvest_nav |
| share_split | 增加 | 不变 | shares_after = entitlement_shares × ratio |
| share_merge | 减少 | 不变 | shares_after = entitlement_shares / ratio |
| bonus_share | 增加 | 不变 | shares_change = entitlement_shares × ratio |
| forced_adjustment | 指定 | 指定 | 直接填写 shares_change / cash_change |

pending 事件**不应用**，但应**拦截快照生成**（同 Trade 硬闸门，避免"漏应用"），而非仅 warning。

#### 10.2.2 事件不影响实时口径

待确认事件不进实时可用现金/份额（与 Trade 冻结同构——pending 卖出既不实际扣份额，pending 事件也不实际改持仓）。

#### 10.2.3 事件依赖权益登记日快照

`confirm_share_change_event` 已校验持仓快照存在——事件以权益登记日快照的份额为基数（`entitlement_shares` = 该日 `portfolio_position.shares`）。

**推论：** 若权益登记日快照被删除（规范 4 补录场景），依赖它的事件须**级联回退为 pending**（新增 `_cascade_unconfirm_share_change_events`，与 `_cascade_unconfirm_subscriptions` 同构），否则重算后事件用错基数。

#### 10.2.4 事件不进现金流 F_t

现金分红（fund→cash）和红利再投（fund shares↑）是资产内部形态转换，组合总视角钱没离开，**不纳入现金 TWR 的 F_t**。`forced_adjustment` 若为外部真实注资/抽资才进 F_t。

#### 10.2.5 事件与 override 独立

事件改成分基金份额/现金（进快照表），override 改非净值资产市值。二者独立，事件走快照主链、不污染 override。

## 11. 已知缺陷：QDII T+2 被闸门误杀

**严重程度：高。** 对持有 QDII（`confirm_days=2`）的组合，QDII 录入后到确认前的每一天快照都被拒。

### 11.1 问题机制

快照硬闸门 `_check_pending_transactions`（`snapshot_service.py` 函数 `_check_pending_transactions`，调查时行号 936-965）对 Trade 的判定：

```python
Trade.trade_date < target_date AND Trade.status == "pending"
```

QDII 调仓 D 日录入（`trade_date=D`），`confirm_date=D+2`。生成 D+1 快照（`target_date=D+1`）时：

- `trade_date=D < D+1` → True
- 状态 pending（合法，本就该 D+2 确认）
- → 闸门误判 → **拒绝生成 D+1 快照** ✗

但 D+1 快照本不该包含这笔 QDII（纳入条件 `confirm_date <= target_date`：D+2 > D+1，应排除）。→ **假阳性**。

**具体日期示例：** 假设 D = 2026-07-08（周三），QDII 调仓 trade_date=07-08，confirm_days=2 → confirm_date=07-10（周五）。生成 07-09（周四）快照时闸门误拒。

### 11.2 根因

用 `trade_date` 判断"该不该已确认"，但真正取决于 `confirm_date`。两者只在 T+1 时重合，QDII(T+2) 和场内(T+0) 均错位。

### 11.3 建议修复（非对称：Trade 侧换字段，Subscription 侧不动）

```python
from sqlalchemy import or_, and_

pending_trades = db.query(Trade).filter(
    Trade.portfolio_code == portfolio_code,
    Trade.status == "pending",
    or_(
        # 已知应确认日且已到期/过期
        and_(Trade.confirm_date.isnot(None), Trade.confirm_date <= target_date),
        # 未知（跨天买入腿 confirm_date=None）回退原逻辑
        and_(Trade.confirm_date.is_(None), Trade.trade_date < target_date),
    ),
).count()
```

Subscription 侧保持 `apply_date < target_date` 不变（其 pending 记录 confirm_date 为 None，且固定 T+1，`apply_date < target` 等价于"应已确认"）。

### 11.4 修复效果

| 交易类型 | 旧逻辑 | 修复后 |
|---|---|---|
| QDII T+2（D 录，D+2 确认），生成 D+1 | 误拒 ✗ | 放行 ✓（confirm_date=D+2 > D+1） |
| T+1 基金（D 录，D+1 确认），D+1 仍 pending | 拒（正确） | 拒（confirm_date=D+1 ≤ D+1） ✓ |
| 场内 T+0（D 录，D 确认），D+1 仍 pending | 拒（正确） | 拒 ✓ |
| 跨天现金买入腿（confirm_date=None），D+1 仍 pending | 拒（正确） | 拒（回退 trade_date<D） ✓ |

## 12. 删快照→重生成安全性分析

**前提：** 级联只碰 Subscription（有级联回退），不碰 Trade（无级联）。Trade 状态不因删快照改变。

### 场景分析

| 场景 | 结果 | 原因 |
|---|---|---|
| A：纯申赎组合（无跨天/QDII） | **安全、自愈** | 删快照→申赎退 pending→regen 自动重确认→闭环 |
| B：有跨天现金买入腿 | **卡死** | 跨天腿 pending + trade_date < target → 闸门拦快照；regen 不自动确认该腿 |
| C：有 QDII T+2 在途 | **卡死** | QDII pending + trade_date < target → 闸门假阳性 + regen 不自动确认 |

### 结论

卡死根因不是级联，而是 (1) 闸门用错字段误杀 + (2) regen 流程缺 Trade 侧自动确认。**闸门修复是规范 4（补录删快照 regen）、规范 5（D+1 处理完）在所有场景下成立的前置依赖。**

## 13. 独立任务：transfer_group 原子翻转

**问题：** 跨天现金转移的"卖出 CASH 已 confirm / 买入 CASH 仍 pending"两腿状态独立——confirm/unconfirm/cancel 一笔，另一笔不联动。可能造成"转出已扣、转入未到"的永久缺口。

**方案：** `transfer_group` 字段已存在，用数据库事务实现两腿原子翻转（confirm/unconfirm/cancel 任一腿，同 `transfer_group` 另一腿一起变）。

**独立性：** 本改造与 override 覆盖层正交——即便未来把现金增减全显式化进 trade 表，原子翻转仍必要。
