## 1. 背景与问题

InvestRing 后端通过 `market_data_service.sync_price_data()` 同步基金价格/净值到
`price_record` 表。在 CLI 实测中暴露出以下问题，导致**无法完成 2020–2026 年历史数据初始化**：

1. **同步阻塞，CLI 60s 超时丢数据**
   `sync_price_data()` 在一个 HTTP 请求生命周期内完成「tushare 拉取 → 内存去重 → 逐条 add → 单次 commit」。
   同步 1 个产品（000051.OF，2020–2026 约 1600 个交易日）超过 60 秒，CLI/HTTP 客户端超时断开，
   后端事务未提交，`price_record` 中该产品记录数为 0。

2. **无异步承接机制**
   全仓搜索 `asyncio` / `BackgroundTasks` / `apscheduler` / `celery` 均无实际使用。
   所有任务（`ir task run nav_sync` 等）均为同步执行，长任务同样会被超时掐断。

3. **无批量写入**
   `price_record` 采用逐条 `db.add()`，仅最后 `db.commit()` 一次。
   代码库虽已存在 `db.bulk_insert_mappings()`（用于 `trading_calendar`），但未用于价格同步。

4. **Tushare 客户端无限流保护**
   `tushare_client.py` 中 `get_fund_daily` / `get_fund_nav` 仅有 3 次重试（退避 1→2→4s），
   **无调用间隔 sleep、无速率控制**。业务文档 §7.4 要求「200 次/分钟，每次调用前等待至少 0.3 秒」。

5. **现有 `nav_sync` 与业务文档 §7.4 存在多处差距（详见 §3）**
   - 增量起点用 `today-7天` 而非 `MAX(date)+1`（§7.4 第二步要求按已存最新日期续传）
   - **缺失分红事件检测**（`fund_div` 接口）—— 本期按决策 D1 **跳过分红检测**，留待后续单独迭代
   - 快照生成逻辑不完整，未按 §7.4 第四步串联
   - 基金筛选用 `market IN ('CN_EXCHANGE','CN_OTC')`：实现上更合理（见 §4.7 说明），
     与 §7.4 的 `product_type IN ('ETF','OEF','LOF')` 在当前数据上结果等价（均 123，0 冲突），且天然排除 CASH

## 2. 目标

1. **支持长时间数据同步不丢数据**：一次同步任务即使运行数小时，调用方断开也不影响数据落库。
2. **支持历史区间批量回填**：可指定 `start_date ~ end_date` 全量回填（如 2020-01-01 ~ today）。
3. **支持断点续传**：增量同步以 `MAX(date)+1` 为起点，失败可重跑（幂等）。
4. **可观测**：任务有状态（pending/running/success/failed/partial）、进度、明细日志。
5. **符合 Tushare 限频要求**：200 次/分钟，每次调用前等待 ≥0.3s，限频自动退避重试。
6. **CLI 不再因超时被掐断**：长任务改为「提交即返回任务 ID」，通过 `sync-job status` 查询进度。
7. **对齐业务文档 §7.4（本期三步）**：净值同步流程（基金列表→逐只净值→快照生成）完整实现；分红检测按决策 D1 本期跳过，留待后续迭代。
8. **每日自动增量调度**：T+1 07:00 自动触发，仅在交易日执行。

## 4. 方案设计

### 4.1 总体思路

引入两层机制，互不冲突：

- **后台任务线程池**（`concurrent.futures.ThreadPoolExecutor`，标准库，无新依赖）：
  承接长耗时同步（历史回填 / 手动增量），提交即返回 `job_id`，后台执行，调用方断开不影响。
- **APScheduler（MySQL JobStore）**：承接每日定时增量调度，`T+1 07:00` 触发，
  仅交易日执行，触发后丢入后台线程池跑 `run_nav_sync`（对齐 §7.4）。
  JobStore 存进现有 MySQL，容器重启不丢调度定义。

### 4.2 后台任务机制（新增）

**新增数据表 `sync_job`：**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int PK | |
| job_type | varchar | `price_history_sync` / `price_incremental_sync` |
| status | varchar | `pending` / `running` / `success` / `partial` / `failed` / `interrupted` |
| params | JSON/text | `{start_date, end_date, scope: all/by_product, products: [...]}` |
| total | int | 计划同步产品数 |
| done | int | 已完成产品数 |
| success_count | int | 成功产品数 |
| failed_count | int | 失败产品数 |
| error_message | text | 失败汇总 |
| created_at / updated_at | datetime | |

**逐产品明细：复用现有 `nav_sync_detail` 表（D4，不新建表）**

- `nav_sync_detail`（已定义于 `Docs/02` §6.5，model `app/models/nav_sync_detail.py`）现有字段：
  `id, task_log_id, product_code, market, nav_date, status, nav_value, source, error_message`。
- **改造**：新增可选字段 `job_id`（关联 `sync_job`，`task_log_id` 保留供现有 `nav_sync` 任务使用）。
  这样 `sync_job` 的逐产品结果直接写入 `nav_sync_detail`，无需维护两套明细表 + 两套写入逻辑。
- 查询某 job 明细：`SELECT * FROM nav_sync_detail WHERE job_id = ?`。

**新增路由（`routers/sync_jobs.py`）：**
- `POST /api/sync-jobs/price` — 提交价格同步任务，立即返回 `job_id`，后台线程执行。
- `GET /api/sync-jobs/{job_id}` — 查询任务状态与进度。
- `GET /api/sync-jobs/{job_id}/details` — 查询逐产品明细（取自 `nav_sync_detail WHERE job_id=?`）。

**并发 sync_job 提交策略（澄清 #12）**：
- 同一时间**只允许一个 price sync job 处于 `running`**。
- 提交时若已有 `running` job，返回 `409 Conflict`（拒绝新建），由调用方决定等待或查询现有 job。
- 理由：多 job 并行拉 Tushare 会突破 200 次/分钟限频；串行 + 单 running 最稳。
- 注：APScheduler 每日定时任务与手动提交的 job 共用同一把「单 running」锁。

**孤儿 running job 恢复（澄清 #11）**：
- 应用启动时（`startup` 事件）扫描 `sync_job` 表中 `status='running'` 的记录：
  这些是本进程或上次运行崩溃遗留的孤儿任务，标记为 `interrupted`（不自动续跑，因幂等可手动重提）。
- 避免用户查 `ir sync-job status` 看到永久 `running` 无法判断真伪。

### 4.3 同步核心改造（关键）

**(a) 单产品同步：`sync_product_prices(db, code, market, start_date, end_date)`**
- **数据源路由（重要）**：进入拉取前，先检查 `product.data_source`：
  - `data_source = 'tushare'` → 走 tushare 客户端（`CN_EXCHANGE`→`get_fund_daily` / `CN_OTC`→`get_fund_nav`）。
  - `data_source = 'akshare'` → 走 akshare 客户端（见 §4.9）：`CN_OTC`→场外净值接口 / `CN_EXCHANGE`→场内 ETF 接口 / **`HK_MUTUAL`→香港互认基金接口**（已确认 akshare 提供）。
  - 其他/未实现 → 记录 `data_source_status='skipped'` 并 continue，不强行用任何源拉。
  - **回写字段（部分现状、部分需新增，已核实）**：
    - **现状已有**：成功路径写 `data_source_status='success'` + `last_sync_at=utcnow()`；失败路径写 `data_source_status='failed'`（market_data_service.py:214-216）。
    - **需新增（现状缺失）**：失败时写 `product.sync_error`（当前异常信息只返回 dict，不落库——评审发现的事实性错误，须补）；`price_record.source` 字段当前恒写 `'tushare'`（错误），须改为取 `product.data_source`（记录实际来源）。
    - **禁止硬编码覆盖 `data_source` 字段**：现状成功路径 `product.data_source = "tushare"` 是错误的，会把非 tushare 产品强行标记为 tushare；改造后只更新 `data_source_status` / `last_sync_at` / `sync_error`（新增），不改写 `data_source` 本身。
- **统一适配层**：两个客户端返回统一结构 `{trade_date: str(YYYYMMDD), unit_price, accumulated_nav|close, pre_close, pct_change}`，下游 upsert 逻辑与数据源无关。
- **批量 upsert**：利用 `uix_price_record` 唯一约束，使用 `db.bulk_insert_mappings()`
  配合 `ON DUPLICATE KEY UPDATE` 原生 SQL（MySQL 兼容），一次提交。
- 返回 `{success, synced_count, message, source}`。

**(b) 批量编排：`run_price_sync_job(job_id)`**
- 根据 `params.scope` 选取产品列表（见 §4.7 基金列表口径）。
- 逐产品调用 (a)，**限流粒度 = 每次 API 调用前 `time.sleep(0.5s)`（≥§7.4 要求的 0.3s）**（澄清 #10：
  是 per-API-call 而非 per-product；单产品若需多次调用如 akshare 单位净值+累计净值，每次调用都 sleep，
  确保不突破 Tushare/akshare 频率上限）。产品级不再额外 sleep。
- 每完成一个产品更新 `sync_job.done/success_count/failed_count` + 写 `nav_sync_detail`（带 job_id）。
- 失败产品记录明细，不中断整体。
- 全程在后台线程，调用方断开不影响。

### 4.4 Tushare 客户端限流增强

在 `tushare_client.py` 增加：
- **调用级限流**（澄清 #10）：在每次 `pro.xxx()` API 调用前 `time.sleep(RATE_INTERVAL)`（默认 **0.5s**，满足 §7.4「≥0.3s」要求）。这是 per-API-call 粒度，确保单产品多次调用（如历史+复权）也限频。
- 优先使用批量接口（一次返回全部交易日，已在 `fund_nav`/`fund_daily` 实现），减少调用次数。
- 限频检测：捕获 Tushare 频率限制错误 → 指数退避（10s→30s→60s）并重试。
- `config.py` 新增 `tushare_rate_interval: float = 0.5`、`tushare_max_retries` 配置项。
- **本期不新增 `fund_div` 接口**（分红检测按决策 D1 跳过，留待后续迭代）。

### 4.5 CLI 改造

- 新增 `ir market sync-all [--start-date] [--end-date] [--scope all|by-product] [--products ...]`：
  提交后台任务，立即返回 `job_id`，打印「任务已提交，用 ir sync-job status <id> 查看进度」。
  - `--products` 格式（澄清 #12）：逗号分隔的 `code|market` 对，如 `--products 000051.OF|CN_OTC,510300.SH|CN_EXCHANGE`。
    对 LOF 产品（同 code 两个 market），必须显式列出两个 `code|market` 才会同步两腿；只给 code 不指定 market 时，按 scope=all 的筛选逻辑推断（即取该产品所有已存在的 market 记录）。
- 新增 `ir sync-job status <id>` / `ir sync-job details <id>`：轮询任务状态与明细。
- 保留现有 `ir market sync`（单产品同步），补充文档说明其仅适合小区间。
- `ir task run nav_sync` 保留为手动增量入口，逻辑按 §4.7 重写。

### 4.6 断点续传

- 增量同步以 `SELECT MAX(date) FROM price_record WHERE product_code=? AND market=?` 为起点，
  起始日期 = 最新日期 + 1 天，结束日期 = 昨天（对齐 §7.4 第二步）。
- 利用 `uix_price_record` 唯一约束实现幂等 upsert：重跑不产生重复。
- `sync_job` 记录已完成产品，重跑时可 `skip_completed=true` 跳过已成功产品（可选）。

### 4.7 净值同步完整流程（对齐 §7.4，本期三步；分红检测按 D1 跳过）

每日增量任务按 §7.4 **第一步→第二步→第四步**严格执行（第三步分红检测本期跳过，见决策 D1）：

```
T+1 07:00 自动触发（或手动 ir task run nav_sync）
┌─ 第一步：获取基金列表 ─────────────────────────────┐
│  SELECT DISTINCT product_code, market FROM product  │
│  WHERE market IN ('CN_EXCHANGE','CN_OTC','HK_MUTUAL')│
│    AND data_source IN ('tushare','akshare')         │  ← market口径选接口(场内fund_daily/场外fund_nav/香港fund_hk)；天然排除CASH(无market)；data_source限定已实现的源(tushare/akshare)
└─────────────────────────────────────────────────────┘
┌─ 第二步：逐只基金同步净值（断点续传） ─────────────┐
│  FOR EACH 基金:                                     │
│    1. SELECT MAX(date) FROM price_record            │
│    2. 起始 = MAX(date)+1 ; 结束 = 昨天(T)           │
│    3. 场外 fund_nav / 场内 fund_daily / 香港 akshare │
│    4. 批量 upsert 到 price_record                   │
│    5. 失败→记日志，继续下一只（下次从断点续）       │
│    限流: 200次/分钟，每次API调用前 sleep≥0.3s        │
└─────────────────────────────────────────────────────┘
┌─ 第四步：自动触发快照生成 ─────────────────────────┐
│  净值同步完成后 → generate_daily_snapshots          │
│  target_date = yesterday(T)  （决策 D3，非 today）  │
│  静默执行，按 §7.5 生成三张快照表                   │
│  复用前序迭代 auto_confirm_after_snapshot（Task 14）│
│  ——快照生成后自动确认 Trade+Event，本期不重复实现   │
└─────────────────────────────────────────────────────┘
```

> **注意**：第三步分红检测（§7.4 原文）**本期按决策 D1 跳过**，不写 `share_change_event`，
> 留待后续单独迭代实现（届时需注意 `event_type` 合法枚举为 `cash_dividend`/`reinvest_dividend` 等，
> 且需映射到 per-portfolio × per-platform，详见评审报告 Critical #2/#3）。
> 第四步快照生成应串联 §7.5 完整流程（portfolio_position → portfolio_value_snapshot → investor_holding，
> 三表 snapshot_date 一致），而非现有 `run_nav_sync` 中零散的快照代码。
> **QDII 时序（D3）**：target_date=yesterday(T) 即前一交易日；QDII 基金在快照中使用 T-1 日净值
> （已有规则）。QDII Trade T+2 不再阻断快照——前序「现金与交易录入重构」Task 3 已将
> `_check_pending_transactions` 的 Trade 分支改为 `confirm_date <= target_date`，D+1 快照不被误杀；
> Subscription 侧 `apply_date < target_date` 按设计保留（QDII 申购在 apply_date 当日由
> auto_confirm_after_snapshot 自动确认）。Doc 09 不需重复处理 QDII 时序。

### 4.8 每日定时调度（APScheduler + MySQL JobStore）

- 新增依赖：`apscheduler`（纯 Python，无 broker）。
- JobStore：`SQLAlchemyJobStore`，连接现有 MySQL（复用 `database_url`），调度定义持久化，容器重启不丢。
- 调度定义：cron `0 7 * * *`（T+1 07:00），job 函数为 `run_nav_sync` 封装（先判断当日是否为交易日，非交易日跳过）。
- **快照 target_date = yesterday(T)**（决策 D3）：定时任务在 T+1 07:00 跑，但快照应落在 T 日（前一交易日），而非 T+1。QDII 基金使用 T-1 日净值（已有规则），详见 §4.7 QDII 时序说明。
- 交易日判断：查 `trading_calendar` 表当日 `is_open`（已同步 2020–2026）。
- job 执行体丢入 §4.2 的后台线程池，避免阻塞 scheduler 主线程。
- 启动时机：FastAPI 应用启动时（`startup` 事件）初始化 scheduler 并恢复 JobStore 中的 job。

### 4.9 akshare 客户端实现

**现状（已核实）**：`akshare` 在代码里**只有数据源开关**（`data_sources.py` 的 `AKSHARE_ENABLED`），
**零拉取实现**；后端容器 `pip show akshare` 未安装，requirements 未列。需从零接入。

**新增 `app/services/akshare_client.py`**，与 `tushare_client.py` 平级，提供统一接口：

- `get_fund_nav_otc(symbol, start_date, end_date)` —— 场外基金净值（CN_OTC）
  - 调用 akshare：`fund_open_fund_info_em(symbol=<6位代码>, indicator="单位净值走势")`
    （返回 date + 单位净值；累计净值可用 indicator="累计净值走势" 二次调用或合并）
  - 适配为统一结构：`{trade_date: YYYYMMDD, unit_price, accumulated_nav}`
- `get_fund_daily_exchange(etf_code, start_date, end_date)` —— 场内 ETF 日线（CN_EXCHANGE）
  - 调用 akshare：`fund_etf_hist_em(etf_code=<6位代码>, period="daily", adjust="")`
    （返回 date + open/close/high/low/volume 等）
  - 适配为统一结构：`{trade_date: YYYYMMDD, close, pre_close, pct_change}`
- `get_fund_hk_mutual(code, start_date, end_date)` —— 香港互认基金净值（HK_MUTUAL）
  - 调用 akshare：香港基金历史净值明细接口（东方财富-天天基金网-香港基金，`code` 传香港互认基金的内地销售代码，如 `1001767344`）。
  - 适配为统一结构：`{trade_date: YYYYMMDD, unit_price, accumulated_nav}`。
  - **`code` 参数格式需实现时实测**：香港互认基金在天天基金网的查询代码可能是 10 位内地代码或另有映射，必须实测确认。
- 统一重试（3 次指数退避）+ 调用间隔（复用 `tushare_rate_interval` 或独立 `akshare_rate_interval`）。

**路由接入（`sync_product_prices` 内）**：
- `product.data_source = 'akshare'` → 按 `market` 分流调：
  - `CN_OTC` → `get_fund_nav_otc`
  - `CN_EXCHANGE` → `get_fund_daily_exchange`
  - `HK_MUTUAL` → `get_fund_hk_mutual`（**本改造中，香港互认基金将以此路径纳入同步**）
- 返回数据经 §4.3 统一适配层 → 相同批量 upsert 逻辑写入 `price_record`，`source` 字段记 `'akshare'`。

**依赖与部署**：
- `requirements.txt` 增加 `akshare`（体积较大、依赖较多，需在 Docker 镜像中安装）。
- 因 akshare 数据源为东方财富网页抓取，**稳定性/限流弱于 tushare**，故仅作为可选数据源，不做主路径。

**实现注意（重要）**：akshare 接口返回字段随版本漂移，具体列名（如净值列是 `单位净值` 还是 `net_value`）
**必须在实现时 `pip install akshare` 后实测校正**，本文档不锁定字段名，以免与运行时版本不符。

### 4.10 初始化脚本修正（根因修复）

**问题根因（已核实 `backend/scripts/init_data.py`）**：第 228–229 行两个香港互认基金
（`1001767346` 摩根国际债券人民币、`1001767344` 摩根国际债券人民币对冲）被错误写成
`market='CN_OTC'` 且未显式设 `data_source`（model 默认 `tushare`）。系统本已支持 `HK_MUTUAL`

**修正内容**：
1. `init_data.py` 第 228–229 行改为：
   ```python
   {'code': '1001767346', 'market': 'HK_MUTUAL', 'name': '摩根国际债券人民币',
    'product_type': 'OEF', 'asset_class_code': 'BOND_GLOBAL', 'confirm_days': 1,
    'is_qdii': False, 'data_source': 'akshare'},
   {'code': '1001767344', 'market': 'HK_MUTUAL', 'name': '摩根国际债券人民币对冲',
    'product_type': 'OEF', 'asset_class_code': 'BOND_GLOBAL', 'confirm_days': 1,
    'is_qdii': False, 'data_source': 'akshare'},
   ```
2. **保持 `(code, market)` 匹配不变（决策 D2）**：`init_data.py` 现有 upsert 逻辑（第 234–239 行，按 `(code, market)` 匹配）**保持不变**。
   对两个香港互认基金，因 `market` 由 `CN_OTC` 改为 `HK_MUTUAL` 后不会覆盖旧记录，需显式处理：
   - **推荐**：在 init 脚本中对这两个 code **先 DELETE 旧 `(code, market='CN_OTC')` 记录，再 INSERT 新的 `(code, market='HK_MUTUAL', data_source='akshare')` 记录**；
     或对该脚本加一段单独 `UPDATE product SET market='HK_MUTUAL', data_source='akshare' WHERE code IN (...) AND market='CN_OTC'`。
   - **不**改为按 code 单键匹配——会破坏 9 只 LOF 基金（同 code 两个 market 各一条，单键匹配会丢失一条腿）。
3. 数据库存量修复：对已在运行的环境，执行一次性 SQL（按 `(code, market)` 精确匹配，避免误伤 LOF）：
   ```sql
   UPDATE product SET market='HK_MUTUAL', data_source='akshare'
   WHERE code IN ('1001767344','1001767346') AND market='CN_OTC';
   ```
   注意：若组合/持仓已引用旧 `CN_OTC` 记录且有关联约束，需先评估，必要时先删旧记录再插 `HK_MUTUAL` 版本（但严禁用 code 单键 UPDATE，会连带改到 LOF 的另一条腿）。

**影响**：修正后产品总数仍为 124，但市场分布变为 `CN_EXCHANGE`(30) + `CN_OTC`(91) + `HK_MUTUAL`(2) + 空(1 CASH)；
纳入同步的产品为 `market IN (...)` 且 `data_source IN ('tushare','akshare')` = **123 个**（排除 CASH）。

   且 `SELECT COUNT(*) FROM (SELECT DISTINCT product_code, market FROM price_record WHERE market IN ('CN_EXCHANGE','CN_OTC','HK_MUTUAL') AND data_source IN ('tushare','akshare')) t` = **123**（排除 1 个 CASH 无 market 产品）。
