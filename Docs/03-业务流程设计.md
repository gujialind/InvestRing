# InvestRing 业务流程设计

> **用途**：详细定义四种核心业务场景的数据处理流程

---

## 关键概念

### 角色权限区分

- **admin（管理员）**：全权操作，可管理所有投资人、组合、交易、产品
- **viewer（观察者）**：只读访问，可查看自己的份额和收益，无管理权限

### 交易类型区分

- **subscription（申购赎回）**：投资人与组合之间的资金往来，影响组合总份额
  
  - 表：`subscription`
  - 字段：`sub_type`（subscribe/redeem）、`apply_date`、`shares`、`unit_price`、`amount`

- **trade（调仓交易）**：组合内部的资产调整，不影响组合总份额
  
  - 表：`trade`
  - 字段：`trade_type`（buy/sell）、`trade_date`、`shares`、`amount`

### 快照属性

- `total_shares` 和 `unit_price` 是 `portfolio_value_snapshot` 表的属性
- **快照每天汇总生成一次**（而非每次交易确认后生成）
- **生成前提**：
  - 净值和分红事件更新完成
  - `apply_date < target_date` 的申购/赎回均已确认（`apply_date == target_date` 的 pending 申购不阻塞当日快照生成）
  - `trade_date < target_date` 的调仓交易均已确认
- **快照与申购确认的关系**：
  - D日快照生成不要求D日的申购已确认（D日申购要到D+1才确认）
  - D+1日确认D日申购时，从D日快照获取净值
  - 快照重算时自动级联回退并重确认：删除D日快照 → 级联回退依赖D日快照的申购 → 重新生成 → 自动确认 apply_date==D 的 pending 申购
- **快照删除的级联行为**：
  - 删除D日快照时，自动回退 `confirm_date == D` 的已确认申购/赎回至 pending
  - 回退时清空 confirm_date、unit_price、shares/amount
- **申购取消确认的快照保护**：
  - unconfirm 前检查 confirm_date 及之后是否已有快照
  - 若有快照，拒绝操作并返回 `SNAPSHOT_DEPENDENCY` 错误
- **冻结字段**：如实记录快照生成时刻的状态（当时 pending 交易的冻结份额/金额）
- **查询可用资源**：需实时计算，不能仅读取快照
  - 可用份额 = 快照份额 - pending赎回/卖出 - confirmed赎回/卖出（快照未生成）
  - 可用现金 = 快照现金 + confirmed申购（快照未生成）- confirmed赎回（快照未生成）- pending买入 - confirmed买入（快照未生成）+ confirmed卖出（快照未生成）
- 查询最新值：`MAX(snapshot_date)`

### 交易日校验规则

- **所有交易操作仅允许在交易日进行**，包括：
  - 申购、赎回
  - 调仓交易（买入、卖出）
  - 现金进出（非净值型资产更新）
- **非交易日操作**：返回错误 `{ error: "NON_TRADING_DAY", message: "非交易日，请等待交易日再提交" }`
- **业务说明**：即使现实中非交易日发生现金变动，也可在交易日记录，不影响组合净值计算
- **交易日判断**：查询 `trading_calendar` 表 `is_open = true`

### 可用资金计算规则

所有可用资金/份额的查询都必须**实时计算**，不依赖快照。

#### 组合层面

**组合可用现金**：

```sql
组合可用现金 = 最新快照现金
              + SUM(confirmed申购金额 WHERE 快照未生成)
              - SUM(confirmed赎回金额 WHERE 快照未生成)
              - SUM(pending买入金额)
              - SUM(confirmed买入金额 WHERE 快照未生成)
              + SUM(confirmed卖出金额 WHERE 快照未生成)
```

**基金可用份额**：

```sql
基金可用份额 = 最新快照份额
              - SUM(pending卖出份额)
              - SUM(confirmed卖出份额 WHERE 快照未生成)
```

#### 投资人层面

**投资人可用份额**：

```sql
投资人可用份额 = 最新快照份额
                - SUM(pending赎回份额)
                - SUM(confirmed赎回份额 WHERE 快照未生成)
```

**投资人可用金额**：可用份额 × 当前净值

#### 为什么需要实时计算？

1. **已确认但快照未生成的交易**：
   
   - 交易在T+1确认，但快照在T+1晚上生成
   - 白天查询时必须包含已确认的交易

2. **Pending交易可能变化**：
   
   - 用户可以随时取消pending交易
   - 快照中的frozen字段只是历史记录，不代表当前状态

3. **业务准确性优先**：
   
   - 防止超额赎回
   - 防止超额买入
   - 防止数据不一致

#### 实现建议

创建统一的实时计算函数：

```python
def get_available_cash(portfolio_code: str) -> Decimal:
    """获取组合可用现金（实时计算）"""
    snapshot = get_latest_position(portfolio_code, 'CASH')
    return snapshot.amount \
        + sum_confirmed_subscribe(portfolio_code, after=snapshot.snapshot_date) \
        - sum_confirmed_redeem(portfolio_code, after=snapshot.snapshot_date) \
        - sum_pending_buy(portfolio_code) \
        - sum_confirmed_buy(portfolio_code, after=snapshot.snapshot_date) \
        + sum_confirmed_sell(portfolio_code, after=snapshot.snapshot_date)

def get_available_shares(portfolio_code: str, product_code: str, market: str) -> Decimal:
    """获取基金可用份额（实时计算）"""
    snapshot = get_latest_position(portfolio_code, product_code, market)
    return snapshot.shares \
        - sum_pending_sell(portfolio_code, product_code, market) \
        - sum_confirmed_sell(portfolio_code, product_code, market, after=snapshot.snapshot_date)

def get_investor_available_shares(portfolio_code: str, investor_code: str) -> Decimal:
    """获取投资人可用份额（实时计算）"""
    snapshot = get_latest_holding(portfolio_code, investor_code)
    return snapshot.shares \
        - sum_pending_redeem(portfolio_code, investor_code) \
        - sum_confirmed_redeem(portfolio_code, investor_code, after=snapshot.snapshot_date)
```

## 1. 组合初始化流程

### 1.1 流程概述

组合初始化包括：创建组合、添加投资人、首次申购启动组合。组合创建时为"空壳"，首次申购确认后组合才正式运行。

### 1.2 组合创建流程

```
管理员发起
┌─────────────────────────────────────────────────────────────┐
│  1. 创建组合记录                                             │
│     - INSERT INTO portfolio (code, name, description)       │
│     - 状态：draft（未初始化）                                 │
│     - 注：不预创建任何快照，等待首次申购确认时创建            │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. 前端跳转                                                 │
│     - 创建成功后，前端自动跳转至该组合详情页                  │
│     - 页面状态显示"待激活"，提示用户执行首次申购              │
│     - 展示操作按钮：「首次申购激活」（admin 可见）            │
└─────────────────────────────────────────────────────────────┘
```

> ⚠️ **重要原则**：快照只记录有份额的状态。组合创建时不预创建现金持仓或净值快照，首次申购确认时才创建真正的快照。投资人通过首次申购自动"加入组合"。

### 1.3 首次申购启动流程

```
投资人发起首次申购
┌─────────────────────────────────────────────────────────────┐
│  1. 校验组合状态                                             │
│     - 检查 portfolio.status = 'draft'                        │
│     - 若 status = 'active'，走正常申购流程                    │
│     - 注：draft 状态表示组合未初始化，无快照                  │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. 前端交互                                                 │
│     - admin 在组合详情页点击「首次申购激活」                  │
│     - 跳转至申购页面 /portfolio/{code}/subscriptions        │
│     - 页面顶部提示："首次申购将激活组合，初始净值固定为 1.0000" │
│     - 用户填写申购金额、选择投资人、申请日期                  │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  3. 创建申购记录                                             │
│     - subscription:                                          │
│       · sub_type = 'subscribe'                              │
│       · amount = 首次申购金额                               │
│       · status = 'pending'                                  │
│       · apply_date = T日                                    │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
T+1日确认
┌─────────────────────────────────────────────────────────────┐
│  4. 确认首次申购                                             │
│     - 初始净值 = 1.0000（固定值，无需获取T日净值）            │
│     - confirmed_shares = amount / 1.0000 = amount           │
│     - 例：首次申购10000元，获得10000份                       │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  5. 创建快照（首次创建，非更新）                              │
│     ┌─────────────────────────────────────────────────────┐ │
│     │ portfolio_value_snapshot（首次创建）:               │ │
│     │   - snapshot_date = 确认日期                        │ │
│     │   - total_value = amount（首次注入资金）            │ │
│     │   - total_shares = amount（份额=金额）              │ │
│     │   - unit_price = 1.0000                             │ │
│     ├─────────────────────────────────────────────────────┤ │
│     │ investor_holding（首次创建，投资人自动加入组合）:   │ │
│     │   - snapshot_date = 确认日期                        │ │
│     │   - shares = amount                                 │ │
│     │   - cost_per_share = 1.0000                         │ │
│     ├─────────────────────────────────────────────────────┤ │
│     │ portfolio_position(CASH)（首次创建）:           │ │
│     │   - snapshot_date = 确认日期                        │ │
│     │   - amount = amount（资金进入组合）                 │ │
│     └─────────────────────────────────────────────────────┘ │
│     注：首次申购确认时才创建快照，组合创建时不预创建          │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  6. 组合状态变更                                             │
│     - UPDATE portfolio SET status = 'active',               │
│                          started_at = CURRENT_TIMESTAMP     │
│     - 组合正式"启动"，可进行正常申购/赎回/调仓               │
│     - 后续申购按正常流程，使用T日净值计算份额                 │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  7. 前端刷新                                                 │
│     - 申购提交成功后，前端跳转回组合详情页                    │
│     - 页面状态显示为"活跃"，展示净值曲线、持仓列表等          │
└─────────────────────────────────────────────────────────────┘
```

### 1.4 数据变化对比

| 实体                       | 属性     | 创建时   | 首次申购确认后         |
| ------------------------ | ------ | ----- | --------------- |
| portfolio                | status | draft | active          |
| portfolio_value_snapshot | -      | 无记录   | 首次创建            |
| investor_holding         | -      | 无记录   | 首次创建（投资人自动加入组合） |
| portfolio_position(CASH) | -      | 无记录   | 首次创建            |

### 1.5 边界条件

| 条件          | 处理方式                                                                                                  |
| ----------- | ----------------------------------------------------------------------------------------------------- |
| 首次申购金额为0    | 拒绝，首次申购必须 > 0                                                                                         |
| 首次申购取消      | subscription.status = 'cancelled'，组合保持 draft 状态                                                       |
| 多位投资人同时首次申购 | 按确认时间先后处理：<br>1. 第一笔确认的申购使组合启动（净值=1.0000）<br>2. 后续申购按正常流程处理，使用T日净值计算份额<br>3. 并发场景：后端使用数据库事务锁，确保确认顺序正确 |
| 组合创建后长期无申购  | 保持 draft 状态，无影响                                                                                       |

### 1.6 关键规则

1. **初始净值固定为 1.0000**
   
   - 首次申购时无需获取净值数据
   - 份额 = 金额 / 1.0000 = 金额
   - 投资人成本价 = 1.0000

2. **组合状态判断**
   
   ```
   未初始化：total_shares = 0
   已启动：total_shares > 0
   ```

3. **首次申购 vs 后续申购**
   
   | 项目   | 首次申购            | 后续申购                    |
   | ---- | --------------- | ----------------------- |
   | 净值来源 | 固定 1.0000       | T日组合净值                  |
   | 份额计算 | shares = amount | shares = amount / nav_T |
   | 成本价  | 1.0000          | 加权平均                    |

## 2. 投资人管理流程

### 2.1 流程概述

投资人管理包括：创建投资人、移除投资人。投资人不直接操作系统，所有申购/赎回操作由 admin 代为执行。

**核心原则**：投资人通过首次申购自动"加入组合"，无需单独添加。移除投资人时创建 shares=0 的特殊快照。

### 2.2 创建投资人流程

```
管理员发起
┌─────────────────────────────────────────────────────────────┐
│  1. 输入投资人信息                                           │
│     - name: 姓名（必填）                                     │
│     - role: 角色（默认 viewer）                              │
│     - phone: 电话（可选）                                    │
│     - email: 邮箱（可选）                                    │
│     - password: 密码（必填，6-32位）                         │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. 校验投资人编码唯一性                                     │
│     - 若编码已存在：拒绝创建，提示"投资人已存在"             │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  3. 创建投资人记录                                           │
│     - INSERT INTO investor (                                │
│         code, name, role, phone, email,                     │
│         password_hash  -- bcrypt 哈希存储                   │
│       )                                                      │
│     - code 自动生成或手动指定                                │
│     - 注：创建投资人记录不等于加入组合                       │
│            投资人通过首次申购自动加入组合                    │
└─────────────────────────────────────────────────────────────┘
```

**认证规则**：

- 所有用户（admin/viewer）必须设置密码
- 密码使用 bcrypt 哈希存储（cost factor: 10）
- 登录时验证密码，连续失败 5 次锁定账户 15 分钟

### 2.3 移除投资人流程

```
管理员发起
┌─────────────────────────────────────────────────────────────┐
│  1. 实时检验投资人可用份额                                   │
│     - available_shares = 最新快照份额                        │
│                         - pending赎回总和                   │
│                         - confirmed赎回（快照未生成）        │
│     - IF available_shares > 0:                              │
│         · 拒绝移除，提示"投资人仍有份额，需先全部赎回"       │
│     - IF available_shares = 0:                              │
│         · 允许移除                                          │
│     注：必须实时计算，不能仅读取快照                         │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. 检查是否最后一位投资人                                   │
│     - 统计组合中有份额的投资人数量（实时计算）               │
│     - IF 是最后一位有份额的投资人 AND available_shares > 0: │
│         · 提示"需先全部赎回或清算组合"                       │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  3. 创建移除快照（特殊快照，标记投资人已退出）               │
│     - INSERT INTO investor_holding (                        │
│         portfolio_code, investor_code,                      │
│         shares = 0, frozen_shares = 0,                      │
│         snapshot_date = 当前日期                            │
│       )                                                      │
│     - 注：这是特殊快照，标记投资人已退出组合                 │
│            后续快照不再为该投资人生成                        │
│            不删除历史快照记录，保留完整历史                   │
└─────────────────────────────────────────────────────────────┘
```

> ⚠️ **说明**：移除投资人时创建 shares=0 的特殊快照，与"占位"不同。这是有意义的业务操作，标记投资人已退出组合，后续快照生成时将跳过该投资人。

### 2.4 admin 代操作规则

所有投资人的申购/赎回操作由 admin 代为执行：

| 操作   | 执行者          | 说明                            |
| ---- | ------------ | ----------------------------- |
| 申购   | admin 代操作    | admin 输入投资人编码、金额，系统记录到对应投资人   |
| 赎回   | admin 代操作    | admin 输入投资人编码、份额，系统从对应投资人份额扣除 |
| 查看份额 | admin 或投资人本人 | 投资人可查看自己的份额和收益                |

### 2.5 边界条件

| 条件          | 处理方式                            |
| ----------- | ------------------------------- |
| 移除有份额的投资人   | 拒绝，提示需先全部赎回                     |
| 移除有冻结份额的投资人 | 拒绝，需等待赎回确认完成                    |
| 移除最后一位投资人   | 若 shares = 0 允许，组合可继续存在         |
| 投资人重新加入组合   | 首次申购确认时创建新的 investor_holding 记录 |

## 2.6 组合关闭流程

### 2.6.1 流程概述

组合关闭是组合生命周期的最后一个阶段。关闭后组合保留所有历史数据，但禁止新的申购、赎回和调仓操作。

### 2.6.2 关闭前检查

```
管理员发起关闭申请
┌─────────────────────────────────────────────────────────────┐
│  1. 检查组合状态                                             │
│     - IF status = 'draft': 拒绝，草稿组合直接删除即可        │
│     - IF status = 'closed': 拒绝，组合已关闭                │
│     - IF status = 'active': 继续检查                        │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. 实时检验待处理交易                                       │
├─────────────────────────────────────────────────────────────┤
│  2.1 检查 pending 申购/赎回                                  │
│      SELECT COUNT(*) FROM subscription                       │
│      WHERE portfolio_code = ? AND status = 'pending'        │
│      IF COUNT > 0: 拒绝，提示先处理完待处理交易              │
│                                                             │
│  2.2 检查 pending 调仓交易                                   │
│      SELECT COUNT(*) FROM trade                              │
│      WHERE portfolio_code = ? AND status = 'pending'        │
│      IF COUNT > 0: 拒绝，提示先处理完待处理交易              │
│                                                             │
│  2.3 检查 pending 份额变动事件                               │
│      SELECT COUNT(*) FROM share_change_event                 │
│      WHERE portfolio_code = ? AND status = 'pending'        │
│      IF COUNT > 0: 拒绝，提示先处理完待处理交易              │
│                                                             │
│  2.4 检查所有投资人的可用份额                                │
│      FOR EACH investor IN 组合:                             │

                              │
                              ▼
```

## 3. 组合申购流程

### 3.1 流程概述

投资人将资金投入组合，获得组合份额。**影响组合总份额**。

**输入单位**：用户输入**金额**（元），系统计算份额。

### 3.2 流程图

```
T日（申请日）
┌─────────────────────────────────────────────────────────────┐
│  1. 投资人发起申购申请                                        │

│     - 创建 subscription 记录：                                 │
│       · sub_type = "subscribe"                               │
│       · status = "pending"                                   │
│       · amount = 申请金额                                    │
│       · apply_date = T日                                     │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. T日组合状态（待确认）                                     │
│     - 快照不变（pending 交易不影响快照）                      │
│     - subscription.status = "pending"                        │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
T+1日（确认日）
┌─────────────────────────────────────────────────────────────┐
│  3. 获取T日组合净值                                          │
│     - nav_T = T日快照的 unit_price                           │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
```

### 3.3 数据变化

| 实体           | T日               | T+1确认后                                  |
| ------------ | ---------------- | --------------------------------------- |
| subscription | status = pending | status = confirmed, shares = amount/nav |
| 查询投资人份额      | 快照份额             | 快照份额 + confirmed申购（快照未生成）               |
| 查询组合现金       | 快照现金             | 快照现金 + confirmed申购金额（快照未生成）             |

### 3.4 成本价计算（加权平均）

```python
# 投资人成本价更新逻辑
if old_shares == 0:
    new_cost = nav_T  # 首次申购，成本价 = 申购日净值
else:
    new_cost = (old_shares * old_cost + confirmed_shares * nav_T) / (old_shares + confirmed_shares)
```

### 3.5 实时检验规则

#### 3.5.1 检验时机

- 投资人发起申购申请时
- 创建申购记录前

#### 3.5.2 检验内容

| 检验项   | 计算公式        | 失败处理               |
| ----- | ----------- | ------------------ |
| 组合状态  | 组合必须已存在     | 返回错误"组合不存在"        |
| 投资人状态 | 投资人必须已添加到组合 | 返回错误"投资人不存在"       |
| 净值有效性 | 组合净值 > 0    | 拒绝申购，提示"组合未初始化"    |
| 申购金额  | 申购金额 > 0    | 拒绝创建，提示"申购金额必须大于0" |

**注**：申购操作不检验可用资金，因为申购是注入资金，增加组合现金。

#### 3.5.3 实时计算说明

- 申购确认后，投资人份额和组合现金立即生效
- 但快照表等待每日汇总生成
- 查询投资人当前份额时需实时计算：快照份额 + 已确认申购（快照未生成）

### 3.6 边界条件

| 条件     | 处理方式                       |
| ------ | -------------------------- |
| 申购金额为0 | 拒绝创建                       |
| 组合不存在  | 返回错误                       |
| 投资人不存在 | 返回错误                       |
| T日净值为0 | 拒绝申购（组合未初始化）               |
| 用户取消申购 | status = "cancelled"，不影响数据 |

## 4. 组合赎回流程

### 4.1 流程概述

投资人从组合取回资金，减少组合份额。**影响组合总份额**。

### 4.2 流程图

```
T日（申请日）
┌─────────────────────────────────────────────────────────────┐
│  1. 投资人发起赎回申请                                        │
│     - 输入：investor_code, portfolio_code, shares            │
│     - 实时校验可用份额：                                      │
│       shares <= 快照份额 - pending赎回 - confirmed赎回（快照未生成）│
│     - 创建 subscription 记录：                                 │
│       · sub_type = "redeem"                                  │
│       · status = "pending"                                   │
│       · shares = 申请份额                                    │
│       · apply_date = T日                                     │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. T日组合状态（待确认）                                     │
│     - 快照不变（pending 交易不影响快照）                      │

                              │

└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  5. 检查组合可用现金                                         │
│     - 可用现金 = 快照现金 - confirmed赎回金额（快照未生成）   │

│         · 需要先卖出部分持仓（触发调仓流程）                   │

```

> ⚠️ **快照生成机制**：快照每天晚上汇总生成，非交易确认后立即生成。交易确认后，查询数据需实时计算（详见"关键概念 - 可用资金计算规则"）。

### 4.3 数据变化

| 实体           | T日               | T+1确认后                                      |
| ------------ | ---------------- | ------------------------------------------- |
| subscription | status = pending | status = confirmed, amount = shares × nav_T |
| 查询投资人份额      | 快照份额 - pending赎回 | 快照份额 - confirmed赎回（快照未生成）                   |
| 查询组合现金       | 快照现金             | 快照现金 - confirmed赎回金额（快照未生成）                 |

### 4.4 净值稳定性验证

```
赎回前：total_value = V, total_shares = S, nav = V/S
赎回后：total_value = V - shares×nav, total_shares = S - shares
       nav_new = (V - shares×nav) / (S - shares)
               = (V - shares×V/S) / (S - shares)
               = V×(S-shares)/S / (S-shares)
               = V/S = nav ✓
```

**结论**：赎回不影响组合净值。

### 4.5 可用份额计算规则

#### 4.5.1 核心原则

> ⚠️ **所有可用份额必须实时计算，不能仅读取快照。**

原因：

1. **pending 交易可能变化**：用户可能取消交易
2. **已确认交易快照未生成**：交易确认后，快照可能还未生成
3. **业务准确性优先**：防止超额赎回

#### 4.5.2 计算公式

```sql
-- 投资人可用份额（实时计算）
可用份额 = 最新快照份额
         - SUM(pending赎回份额)
         - SUM(confirmed赎回份额 WHERE 快照未生成)
```

#### 4.5.3 示例

假设投资人持有 1000 份：

| 日期         | 事件       | 快照 shares | 快照 frozen_shares | pending赎回 | confirmed赎回（快照未生成） | 可用份额 |
| ---------- | -------- | --------- | ---------------- | --------- | ------------------ | ---- |
| T-1日       | 无        | 1000      | 0                | 0         | 0                  | 1000 |
| T日 09:00   | 申请赎回300份 | -         | -                | 300       | 0                  | 700  |
| T日 晚上快照    | 生成快照     | 1000      | 300              | 300       | 0                  | 700  |
| T+1日 10:00 | 确认赎回300份 | 1000      | 300              | 0         | 300                | 700  |
| T+1日 晚上快照  | 生成快照     | 700       | 0                | 0         | 0                  | 700  |

**说明**：

- 快照每天晚上生成，`frozen_shares` 如实记录快照生成时刻的 pending 赎回总和
- 查询可用份额时仍需实时计算，因为快照生成后可能发生新的交易或交易被取消

#### 4.5.4 查询可用份额

```sql
-- 实时计算可用份额（快照shares - pending赎回 - confirmed赎回快照未生成）
SELECT 
    h.shares - COALESCE(
        (SELECT SUM(s.shares) 
         FROM subscription s 
         WHERE s.portfolio_code = h.portfolio_code 
           AND s.investor_code = h.investor_code 
           AND s.sub_type = 'redeem' 
           AND s.status = 'pending'),
        0
    ) - COALESCE(
        (SELECT SUM(s.shares) 
         FROM subscription s 
         WHERE s.portfolio_code = h.portfolio_code 
           AND s.investor_code = h.investor_code 
           AND s.sub_type = 'redeem' 
           AND s.status = 'confirmed'
           AND s.confirm_date > h.snapshot_date),
        0
    ) AS available_shares
FROM investor_holding h
WHERE h.portfolio_code = ? AND h.investor_code = ?
ORDER BY h.snapshot_date DESC LIMIT 1;
```

### 4.6 实时检验规则

#### 4.6.1 检验时机

- 投资人发起赎回申请时
- 创建赎回记录前

#### 4.6.2 检验内容

| 检验项         | 计算公式                                                                                                            | 失败处理               |
| ----------- | --------------------------------------------------------------------------------------------------------------- | ------------------ |
| **投资人可用份额** | `投资人可用份额 = 最新快照份额 - pending赎回总和 - confirmed赎回（快照未生成）`                                                           | 拒绝赎回，提示"可用份额不足"    |

```
┌─────────────────────────────────────────────────────────────┐
│  第二步：创建赎回记录（pending状态）                          │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  第三步：T+1确认时检验组合现金                                │
├─────────────────────────────────────────────────────────────┤
```

- **投资人可用份额**：必须实时计算，防止超额赎回
- **组合可用现金**：确认时检验，确保有足够现金支付赎回金额
- pending赎回记录创建后立即可用份额减少
- 取消赎回后立即可用份额恢复

| 全部赎回        | 检查是否最后一位投资人，可能触发组合清算                 |
| 用户取消赎回      | status = "cancelled"，下次快照生成时冻结份额自动减少 |

## 5. 组合调仓流程

### 5.1 流程概述

组合内部资产调整（卖出基金获得现金，再用现金买入基金），**不影响组合总份额**。

> ⚠️ **核心约束**：调仓必须通过现金中转，不能直接基金对基金转换。
> 
> - **卖出基金**：必须对应现金资产增加（卖出所得资金进入组合现金池）
> - **买入基金**：必须对应现金资产减少（从组合现金池支出）
> - 卖出和买入是两个独立交易，可同时提交但独立确认（T+1/T+2不同日）

### 5.2 流程图

```
T日（申请日）
┌─────────────────────────────────────────────────────────────┐
│  1. 创建交易记录                                             │
│     - 卖出交易：trade_type = "sell", status = "pending"      │
│       · 实时校验：卖出份额 <= 基金可用份额                   │
│       · 卖出所得资金将增加组合现金                           │
│     - 买入交易：trade_type = "buy", status = "pending"       │
│       · 实时校验：买入金额 <= 组合可用现金                   │
│       · 买入资金从组合现金支出                               │
│     注：卖出和买入独立校验，卖出pending不自动增加可用现金    │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  2. T日组合状态                                              │
│     - 快照不变（pending 交易不影响快照）                      │
│     - 组合总份额不变 ✓                                       │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
T+1日或T+N日（确认日）
┌─────────────────────────────────────────────────────────────┐
│  3. 获取确认信息                                             │
│     - 卖出：T日净值/收盘价，计算确认金额                      │
│     - 买入：T日净值，计算确认份额                            │
│     - 净值取值规则：                                          │
│       · 普通基金：使用T日（申请日）净值                       │
│       · QDII基金：必须使用T日净值，若未同步则拒绝确认         │
│       · 确认时间：场内T+0，场外T+1，QDII T+2                 │
│     - 重要：调仓交易确认时禁止向前查找替代净值               │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  4. 确认完成                                                 │
│     - trade.status = "confirmed"                             │
│     - 卖出和买入独立确认（可能不同日）                        │
│     - 交易立即生效，后续快照生成时汇总写入                    │
└─────────────────────────────────────────────────────────────┘
```

> ⚠️ **快照生成机制**：快照每天晚上汇总生成，非交易确认后立即生成。交易确认后，查询数据需实时计算（详见"关键概念 - 可用资金计算规则"）。

### 5.3 数据变化

| 实体          | T日               | 卖出确认后                                 | 买入确认后                                   |
| ----------- | ---------------- | ------------------------------------- | --------------------------------------- |
| trade(sell) | status = pending | status = confirmed                    | status = confirmed                      |
| trade(buy)  | status = pending | status = pending                      | status = confirmed                      |
| 查询基金A份额     | 快照份额 - pending卖出 | 快照份额 - confirmed卖出（快照未生成）             | 同左                                      |
| 查询基金B份额     | 快照份额             | 快照份额                                  | 快照份额 + confirmed买入（快照未生成）               |
| 查询组合现金      | 快照现金 - pending买入 | 快照现金 + confirmed卖出 - pending买入（快照未生成） | 快照现金 + confirmed卖出 - confirmed买入（快照未生成） |

> ⚠️ **关键说明**：
> 
> - 卖出pending时，基金可用份额减少，但组合现金不增加（需等待确认）
> - 买入只能使用已有的可用现金，不能使用卖出pending的"预期现金"
> - 若现金不足，可先提交卖出，确认后再提交买入（分两步操作）

### 5.4 实时检验规则

#### 5.4.1 检验时机

- 创建调仓交易记录前
- 卖出基金时检验可用份额
- 买入基金时检验可用现金

#### 5.4.2 检验内容

| 检验项             | 计算公式                                                                                                            | 失败处理            |
| --------------- | --------------------------------------------------------------------------------------------------------------- | --------------- |
| **基金可用份额**（卖出时） | `基金可用份额 = 最新快照份额 - pending卖出总和 - confirmed卖出（快照未生成）`                                                            | 拒绝卖出，提示"可用份额不足" |
| **组合可用现金**（买入时） | `组合可用现金 = 快照现金 + confirmed申购（快照未生成） - confirmed赎回（快照未生成） - pending买入 - confirmed买入（快照未生成） + confirmed卖出（快照未生成）` | 拒绝买入，提示"可用现金不足" |

#### 5.4.3 检验流程

```
用户发起调仓申请
┌─────────────────────────────────────────────────────────────┐
│  第一步：检验卖出基金的可用份额                               │
├─────────────────────────────────────────────────────────────┤
│  IF 卖出操作:                                                │
│    available_shares = get_available_shares(portfolio, 基金A)│
│    IF 申请卖出份额 > available_shares:                       │
│      拒绝，提示"基金A可用份额不足"                           │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  第二步：检验买入基金的可用现金                               │
├─────────────────────────────────────────────────────────────┤
│  IF 买入操作:                                                │
│    available_cash = get_available_cash(portfolio)           │
│    IF 申请买入金额 > available_cash:                         │
│      拒绝，提示"可用现金不足"                                │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  第三步：创建交易记录                                         │
│     - 卖出交易：status = 'pending'                           │
│     - 买入交易：status = 'pending'                           │
└─────────────────────────────────────────────────────────────┘
```

#### 5.4.4 实时计算说明

- **基金可用份额**：卖出时必须实时计算，防止超额卖出
- **组合可用现金**：买入时必须实时计算，防止超额买入
- pending交易创建后立即可用资源减少
- 取消交易后立即可用资源恢复

### 5.5 边界条件

| 条件             | 处理方式                                                              |
| -------------- | ----------------------------------------------------------------- |
| 卖出份额 > 可用份额    | 拒绝（可用份额 = 快照份额 - pending卖出总和 - confirmed卖出快照未生成）                  |
| 买入金额 > 可用现金    | 拒绝（可用现金 = 快照现金 + confirmed卖出快照未生成 - pending买入 - confirmed买入快照未生成） |
| 现金不足但想调仓       | 分两步操作：先卖出基金等待确认，确认后再买入目标基金                                        |
| 卖出后清仓          | 快照中 shares=0，持仓记录保留                                               |
| 用户取消           | status = "cancelled"，可用份额/现金自动恢复                                  |
| 确认失败（如基金已清盘）   | status = "cancelled"，可用份额/现金自动恢复                                  |
| 卖出和买入同日提交      | 允许，但买入金额不能超过已有可用现金（不含卖出pending）                                   |
| 卖出确认，买入pending | 允许，卖出所得现金可用于买入                                                    |

### 5.6 调仓操作模式

#### 模式一：同时提交卖出和买入（推荐用于现金充足时）

```
场景：组合有充足现金，想调仓

操作：
1. 同时提交卖出基金A、买入基金B
2. 卖出基金A：pending状态，基金A可用份额减少
3. 买入基金B：pending状态，组合现金减少
4. T+1确认卖出：组合现金增加
5. T+1/T+2确认买入：基金B份额增加

前提条件：
- 组合可用现金 >= 买入金额
- 基金A可用份额 >= 卖出份额
```

#### 模式二：先卖后买（用于现金不足时）

```
场景：组合现金不足，想卖出基金A买入基金B

操作：
1. 先提交卖出基金A
2. 等待T+1确认，卖出所得资金进入组合现金
3. 确认后再提交买入基金B
4. 等待T+1/T+2确认

优点：
- 可用现金不足时也能完成调仓
- 资金流转清晰

缺点：
- 需要两次操作
- 时间跨度较长（可能需要T+2到T+3天完成）
```

## 6. 基金份额变动事件处理流程

### 6.1 流程概述

基金公司发起的份额变动事件：分红、拆分、合并、送股等。**影响基金持仓份额，但不影响组合总份额**。

### 6.2 事件类型与计算公式

| 事件类型   | 代码                | 份额变化 | 现金变化 | 计算公式                                                         |
| ------ | ----------------- | ---- | ---- | ------------------------------------------------------------ |
| 现金分红   | cash_dividend     | 不变   | 增加   | cash_change = entitlement_shares × div_cash                  |
| 分红再投资  | reinvest_dividend | 增加   | 不变   | shares_change = entitlement_shares × div_cash / reinvest_nav |
| 份额拆分   | share_split       | 增加   | 不变   | shares_after = entitlement_shares × ratio                    |
| 份额合并   | share_merge       | 减少   | 不变   | shares_after = entitlement_shares / ratio                    |
| 红股（送股） | bonus_share       | 增加   | 不变   | shares_change = entitlement_shares × ratio                   |
| 强制调整   | forced_adjustment | 指定   | 指定   | 直接填写 shares_change / cash_change                             |

### 6.3 现金分红处理逻辑

现金作为独立持仓：product_code = 'CASH'，market = NULL，shares = NULL，amount = 现金金额

> **说明**：统一使用 `CASH` 作为现金产品代码，不区分币种。如需多币种支持，后续可扩展为 `CASH_CNY`/`CASH_USD`/`CASH_HKD`。

除息日快照生成：

1. 基金持仓：shares 不变，unit_price 除权后净值
2. 现金持仓：amount = 上次金额 + cash_change
3. 组合总市值不变（市值下降 + 现金增加）

### 6.10 实时检验规则

```
│  第二步：获取权益登记日份额                                   │

│     IF entitlement_shares = 0:                              │
│       标记为 skipped                                        │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  第三步：计算并执行调整                                       │
│     根据事件类型计算 shares_change / cash_change            │
│     等待快照生成时汇总更新                                   │
└─────────────────────────────────────────────────────────────┘
```

#### 6.10.4 实时计算说明

- **权益登记日持仓快照**：必须存在才能确认事件
- 份额变动事件不涉及可用资源的实时检验（不影响pending交易）
- 变动结果等待快照生成时汇总更新

### 6.11 边界条件

| 条件         | 处理方式                       |
| ---------- | -------------------------- |
| 事件日期无持仓    | 不处理，标记为 skipped            |
| 多个组合持有同一基金 | 每个组合独立处理                   |
| 用户拒绝确认     | status = "cancelled"，不影响持仓 |
| 事件信息不完整    | 拒绝创建，要求补充                  |
| 权益登记日份额为0  | 不产生现金变化，标记为 skipped        |

## 7. 每日计算流程

### 7.1 流程概述

每日计算流程包含三个主要环节：净值同步、快照生成、份额平衡校验。其中，快照生成涉及三张表，按照固定顺序执行，保证数据一致性。

**三张快照表**：

- `portfolio_position`（组合持仓快照表）：记录组合每天结束时的持仓状态
- `portfolio_value_snapshot`（组合市值快照表）：记录组合每天结束时的市值和净值
- `investor_holding`（投资人持仓快照表）：记录投资人每天结束时的份额状态

**核心原则**：

1. 三张表**每天汇总生成一次**（即使当天没有申购赎回）
2. 三张表的 `snapshot_date` **必须一致**
3. 三张表**按固定顺序生成**：portfolio_position → portfolio_value_snapshot → investor_holding
4. 快照中冻结字段**如实记录当天结束时刻状态**
5. 查询可用份额时仍需**实时计算 pending 交易**

### 7.2 触发方式

| 方式   | 触发时机          | 日期范围                | 组合选择     |
| ---- | ------------- | ------------------- | -------- |
| 手动触发 | admin点击"更新净值" | 可选择，受安全上限约束         | 可勾选，默认全选 |
| 自动触发 | 净值同步完成后       | 默认范围（上次快照+1 至 安全上限） | 所有组合     |

### 7.3 安全日期范围计算

**示例1：有待确认事件**

```
待确认事件日期：2026-04-20, 2026-04-22, 2026-04-25
安全日期上限 = MIN(2026-04-20, 2026-04-22, 2026-04-25) - 1
            = 2026-04-20 - 1
            = 2026-04-19

说明：只能更新到 04-19，因为 04-20 有待确认事件
```

**示例2：无待确认事件**

```
安全日期上限 = 昨天
说明：可以更新到昨天
```

**示例3：多组合情况**

```
组合A安全上限：2026-04-19
组合B安全上限：2026-04-21
组合C安全上限：2026-04-18

最终安全上限 = MIN(2026-04-19, 2026-04-21, 2026-04-18)
            = 2026-04-18

说明：取交集，保证所有组合都能安全更新
```

### 7.5 快照生成流程

快照生成是每日计算的核心环节，按照固定顺序生成三张快照表，保证数据一致性。

#### 7.5.1 生成前提

1. **净值数据已同步**：price_record 表中有所需日期的净值数据
2. **分红事件已处理**：当天应确认的分红事件都已确认
3. **交易已确认**：确认日期 ≤ 昨天的交易都已处理完

#### 7.5.2 生成顺序

**三张表必须按以下顺序生成**：

1. **portfolio_position**（组合持仓快照表）
2. **portfolio_value_snapshot**（组合市值快照表）
3. **investor_holding**（投资人持仓快照表）

**原因**：后两张表的计算依赖前一张表的数据。

#### 7.5.3 详细流程

#### 7.5.4 关键说明

**快照与实时计算的关系**：

```
┌─────────────────────────────────────────────────────────────┐
│                   快照生成与可用资金计算                      │
├─────────────────────────────────────────────────────────────┤
│ 1. 所有快照表每天汇总生成一次（即使当天无交易）              │
│ 2. 交易确认后，所有变化等待快照生成时汇总                    │
│ 3. 快照中冻结字段如实记录当天结束时刻状态                    │
│ 4. **所有可用资金/份额必须实时计算**                        │
│    - 组合可用现金 = 快照现金 + confirmed申购 - confirmed赎回│
│                      - pending买入 - confirmed买入          │
│    - 基金可用份额 = 快照份额 - pending卖出 - confirmed卖出  │
│    - 投资人可用份额 = 快照份额 - pending赎回                │
│ 5. 实时计算原因：                                           │
│    - pending交易可能取消                                    │
│    - 已确认交易快照未生成                                   │
│    - 业务准确性优先                                         │
└─────────────────────────────────────────────────────────────┘
```

**冻结字段处理**：

- 快照中的 `frozen_shares` 和 `frozen_amount` **如实记录当天结束时刻状态**
- 查询可用份额时仍需**实时计算**：`可用份额 = 快照shares - 当前pending赎回总和`
- 原因：pending 交易可能取消或确认时间变化，快照只是历史记录

**investor_holding 生成规则**：

- **每天汇总生成一次**，即使当天没有申购赎回
- 保证三张表的 `snapshot_date` 一致
- 保证投资人份额总和 = 组合总份额（份额平衡校验）

### 7.6 重新计算历史数据规则

#### 7.6.1 重新计算历史数据规则

当需要重新计算历史数据时（如用户补录历史交易后）：

1. **删除已有快照**（三张表全部删除）
      DELETE FROM portfolio_position 
      WHERE portfolio_code = ? AND snapshot_date BETWEEN start_date AND end_date;
      DELETE FROM portfolio_value_snapshot 
      WHERE portfolio_code = ? AND snapshot_date BETWEEN start_date AND end_date;
      DELETE FROM investor_holding 
      WHERE portfolio_code = ? AND snapshot_date BETWEEN start_date AND end_date;

2. **重新计算并创建新快照**
   
   * 按第7.5节流程逐日生成三张快照表
   * 保证三张表的生成顺序和一致性
   * 跳过非交易日
   * 每日独立事务，某日失败不影响其他日期

**说明**：

* 三张快照表都需要删除并重新生成，保证数据一致性
* 支持指定时间区间重算，也支持全量重算
* 重算前需校验依赖数据（pending交易、净值数据、分红事件等）

#### 7.6.2 异常处理

| 异常场景           | 处理方式                  |
| -------------- | --------------------- |
| 单只基金净值获取失败     | 记录日志，继续下一只，下次执行时从断点继续 |
| QDII净值未公布      | 正常现象，下次执行时自动获取        |
| 安全日期上限早于创建日期   | 终止流程，无有效更新范围          |
| 分红信息获取失败       | 记录日志，继续下一只，不影响净值同步    |
| 分红事件已存在        | 跳过，不重复创建              |
| API调用超限（429错误） | 等待1分钟后重试，记录日志         |
| API调用失败（网络异常）  | 等待30秒后重试，最多3次，记录日志    |
| 份额不平衡          | 回滚事务，记录错误日志，通知admin   |
| 快照删除失败         | 回滚事务，记录错误日志           |

### 7.7 计算公式详解

#### 7.7.1 组合市值计算

```python
def calculate_portfolio_value(portfolio_code: str, date: date) -> Decimal:
    """计算组合指定日期市值

    注意：冻结份额和冻结金额仍计入市值
    - 冻结份额（赎回中）：份额仍归属组合，承担净值波动
    - 冻结金额（申购中）：资金仍归属组合，等待确认
    """
    total_value = Decimal("0")

    # 获取该日期的持仓快照
    positions = get_positions_at_date(portfolio_code, date)

    for pos in positions:
        if pos.shares is not None:
            # 净值型资产：份额 × 净值
            product = get_product(pos.product_code, pos.market)

            if product.is_qdii:
                # QDII基金：计算持仓市值时使用T-1日净值
                # 原因：T日净值要T+2才公布，T日无法获取
                prev_date = prev_trading_day(date, 1)  # 前一交易日
                nav = get_nav(pos.product_code, prev_date)
            else:
                # 普通基金：直接使用T日净值
                nav = get_nav(pos.product_code, date)

            market_value = pos.shares * nav
            total_value += market_value

        elif pos.amount is not None:
            # 非净值型资产：直接取金额
            total_value += pos.amount

    return total_value
```

> ⚠️ **QDII净值取值规则总结**：
> 
> | 场景            | 净值取值规则          | 原因               |
> | ------------- | --------------- | ---------------- |
> | **调仓交易确认**    | 必须使用T日（申请日）净值   | 确保份额计算准确，避免日期错配  |
> | **快照生成/市值计算** | 使用T-1日（前一交易日）净值 | T日净值T+2才公布，T日不可用 |
> 
> **重要区别**：
> 
> - 调仓确认时：如果QDII T日净值未同步，应拒绝确认或要求管理员手动指定，**禁止向前查找替代**
> - 快照生成时：由于是事后计算，T-1日净值已经可用，直接使用即可

#### 7.7.2 组合净值计算

```python
def calculate_portfolio_nav(total_value: Decimal, total_shares: Decimal) -> Decimal:
    """计算组合净值"""
    if total_shares <= 0:
        return Decimal("1.0000")  # 初始净值

    nav = total_value / total_shares
    return nav.quantize(Decimal("0.0001"))  # 保留4位小数
```

#### 7.7.3 投资人持有市值计算

```python
def calculate_investor_value(investor_code: str, portfolio_code: str) -> dict:
    """计算投资人持有市值和收益"""
    # 获取投资人最新份额快照
    holding = get_latest_holding(investor_code, portfolio_code)

    # 获取组合最新净值
    snapshot = get_latest_snapshot(portfolio_code)
    nav = snapshot.unit_price if snapshot else Decimal("1.0000")

    # 持有市值
    market_value = holding.shares * nav

    # 投入成本
    cost = holding.shares * holding.cost_per_share

    # 累计收益
    profit = market_value - cost

    # 收益率
    profit_rate = (nav - holding.cost_per_share) / holding.cost_per_share

    return {
        "shares": holding.shares,
        "market_value": market_value,
        "cost": cost,
        "profit": profit,
        "profit_rate": profit_rate * 100  # 转为百分比
    }
```

### 7.8 份额平衡校验

```python
def validate_share_balance(portfolio_code: str) -> bool:
    """校验组合份额平衡"""
    # 获取最新快照的组合总份额
    snapshot = get_latest_snapshot(portfolio_code)
    total_shares = snapshot.total_shares if snapshot else Decimal("0")

    # 获取最新日期所有投资人份额之和
    latest_date = get_latest_holding_date(portfolio_code)
    shares_sum = sum_holding_shares(portfolio_code, latest_date)

    # 比较（允许0.0001误差）
    return abs(total_shares - shares_sum) < Decimal("0.0001")
```

### 7.9 执行时机汇总

| 任务     | 执行时间         | 触发方式      |
| ------ | ------------ | --------- |
| 净值同步   | T+1日 07:00   | 定时任务 + 手动 |
| 分红事件检测 | 净值同步后自动执行    | 自动触发      |
| 快照生成   | 净值同步和分红检测完成后 | 自动触发 + 手动 |

**说明**：

- 净值同步安排在次日早上7点，是因为数据源（如Tushare）的基金净值通常在晚间更新，次日早上同步可避免数据延迟问题
- 分红事件默认红利再投资，状态为pending，需人工确认后生效
- 快照生成按照固定顺序生成三张表，保证数据一致性

### 7.8 QDII基金净值处理完整规则

#### 7.8.1 核心原则

QDII基金由于跨境投资的特性，净值公布存在T+2延迟，在不同业务场景下有不同的处理规则。

#### 7.8.2 调仓交易场景

**规则**：必须使用T日（申请日）净值，禁止向前查找替代。

**流程**：

```
T日：用户提交调仓申请（买入/卖出QDII基金）
  ↓
系统记录trade.status = "pending"
  ↓
T+2日：QDII基金T日净值公布
  ↓
管理员调用确认接口，传入T日净值（或系统自动获取）
  ↓
系统使用T日净值计算份额/金额
  ↓
trade.status = "confirmed"
```

**异常处理**：

- 如果T+2日T日净值仍未同步：拒绝确认，返回错误`QDII_NAV_NOT_AVAILABLE`
- 管理员可手动指定净值：通过`price`参数传入

**代码示例**：

```python
# 错误的做法 ❌
nav = get_latest_available_nav(product_code)  # 可能取到T-1日净值

# 正确的做法 ✅
nav = get_nav_on_date(product_code, trade_date)  # 必须取T日净值
if not nav:
    raise ValueError(f"QDII基金{product_code}在T={trade_date}的净值尚未同步")
```

#### 7.8.3 快照生成场景

**规则**：使用T-1日（前一交易日）净值。

**原因**：

- 在T日计算组合持仓市值时，QDII基金的T日净值尚未公布
- T-1日净值已经在T-1+2=T+1日公布，是可用的最新净值
- 使用T-1日净值能更准确反映组合的实际价值

**代码示例**：

```python
def calculate_position_market_value(position, target_date):
    """计算持仓市值"""
    product = get_product(position.product_code, position.market)

    if product.is_qdii:
        # QDII：使用T-1日净值
        prev_date = prev_trading_day(target_date, 1)
        nav = get_nav(position.product_code, prev_date)
    else:
        # 普通基金：使用T日净值
        nav = get_nav(position.product_code, target_date)

    return position.shares * nav
```

#### 7.8.4 数据校验规则

在重算历史快照前，需要校验净值数据完整性：

**普通基金**：检查`target_date`当日净值是否存在

**QDII基金**：检查`prev_trading_day(target_date, 1)`（T-1日）净值是否存在

**代码示例**：

```python
def validate_nav_data(product, target_date):
    if product.is_qdii:
        # QDII：检查T-1日净值
        check_date = prev_trading_day(target_date, 1)
    else:
        # 普通基金：检查T日净值
        check_date = target_date

    nav = get_nav(product.code, check_date)
    if not nav:
        raise ValueError(f"产品{product.code}在{check_date}无净值数据")
```

#### 7.8.5 常见误区

| 误区                        | 正确理解                  |
| ------------------------- | --------------------- |
| "QDII应该向前查找最近可用的净值"       | ❌ 调仓确认时必须用T日净值，不能向前查找 |
| "QDII在快照中也应该用T日净值"        | ❌ 快照生成时T日净值不可用，应用T-1日 |
| "QDII确认时间是T+2，所以净值也是T+2的" | ❌ 确认时间是T+2，但净值是T日的    |
| "所有场景下QDII都用T-1日净值"       | ❌ 仅快照生成时用T-1日，调仓确认用T日 |



### 7.10 非净值型资产更新流程

#### 7.10.1 流程概述

非净值型资产（如现金）的持仓金额更新是特殊的业务操作，允许管理员手动调整组合在特定平台的现金余额。**影响组合总市值**。

**核心特点**：
- 不通过申购赎回或调仓交易产生
- 直接修改 `portfolio_position` 表的 `amount` 字段
- 支持多平台分别管理现金
- 必须在交易日进行
- 更新后立即生效，等待快照生成时汇总

##### 7.10.4.4 实时计算说明
- **更新立即生效**：portfolio_position 表的 amount 字段立即更新
- **组合现金实时计算**：可用现金 = 快照现金 + confirmed申购 - confirmed赎回 - pending买入 - confirmed买入 + confirmed卖出 + 本次更新差额
- **等待快照汇总**：更新的金额会在下一次快照生成时被纳入计算

#### 7.10.5 边界条件

| 条件 | 处理方式 |
|------|---------|
| 金额为负数 | 拒绝更新 |
| 平台代码为空 | 拒绝更新 |
| 平台不存在 | 拒绝更新 |
| 非交易日 | 拒绝更新 |
| 组合不存在 | 拒绝更新 |
| 同一组合+平台+日期已存在记录 | 更新现有记录的 amount |
| 同一组合+平台+日期无记录 | 创建新记录 |
| 多平台现金持仓 | 允许，每个平台独立管理 |
| 重复更新同一天同一平台 | 覆盖之前的金额 |

#### 7.10.6 与快照生成的关系

**更新时机与快照的关系**：

```
场景1：快照生成前更新
T日早上：管理员更新现金金额
T日晚上：快照生成时，使用更新后的金额

场景2：快照生成后更新
T日晚上快照已生成
T+1日早上：管理员更新现金金额
  → 创建 T+1日的新持仓记录
  → T日的快照保持不变
  → T+1日晚上快照生成时，使用新金额
```

**关键原则**：
- 非净值资产更新**不触发即时快照生成**
- 更新结果等待每日快照汇总时纳入计算
- 每次更新创建或更新一条 `portfolio_position` 记录
- 快照生成时，汇总所有已确认的交易和更新

#### 7.10.7 多平台现金管理

**业务场景**：
组合可能在不同券商平台持有现金，需要分别管理。

**数据模型支持**：
```sql
-- 唯一约束支持多平台
```

| 异常场景 | 处理方式 |

## 8. 核心原则总结

### 8.1 份额变化原则

| 操作类型   | 组合总份额 | 投资人份额 | 基金持仓份额   |
| ------ | ----- | ----- | -------- |
| 申购     | 增加    | 增加    | 不变（现金增加） |
| 赎回     | 减少    | 减少    | 不变（现金减少） |
| 调仓     | 不变    | 不变    | 变化       |
| 份额变动事件 | 不变    | 不变    | 变化       |

### 8.2 待确认处理原则

```
┌─────────────────────────────────────────────────────────────┐
│                     待确认资产处理规则                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ 组合层面（申购/赎回）                                        │
│   T日：不计入市值，不改变份额                                │
│   T+N确认后：计入市值，改变份额                              │
│                                                             │
│ 基金层面（买入/卖出）                                        │
│   T日：冻结相关持仓                                         │
│   T+N确认后：更新持仓份额                                   │
│   期间市值按申购金额计入（已归属组合）                       │
│                                                             │
│ 份额变动事件                                                 │
│   待确认：不处理                                            │
│   确认后：更新持仓                                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 8.3 净值稳定性

| 操作      | 净值变化 | 原因                 |
| ------- | ---- | ------------------ |
| 申购      | 不变   | 份额和市值同步增加          |
| 赎回      | 不变   | 按申请日净值计算，份额和市值同步减少 |
| 调仓      | 可能变化 | 不同基金净值波动不同         |
| 现金分红    | 不变   | 分红已反映在基金净值下跌       |
| 份额拆分/合并 | 不变   | 份额和净值同步调整          |
