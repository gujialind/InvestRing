```
          └────────────────────────┘
```

### 1.2 Trade 表的三个写入入口

Trade 表是系统的核心枢纽，有三个独立的写入入口：

| 写入方 | 文件位置 | transfer_group 前缀 | CASH trade 类型 | 创建时状态 |
|--------|----------|---------------------|-----------------|-----------|
| subscription confirm | `subscription_service.py:122-138` | `sub_{subscription.id}` | buy(申购) / sell(赎回) | 直接 confirmed |
| trade create | `trades.py:367-393` | `rebal_{uuid12}` | sell(买基金) / buy(卖基金) | pending |
| cash transfer create | `cash_transfers.py:141-176` | `{uuid12}` (无前缀) | sell + buy (成对) | pending 或 confirmed |

**关键设计**：`share_change_event` **不写 Trade 表**。事件对现金的影响通过 `compute_cash_balance()` 直接从 event 表读取 `cash_change` 字段，不生成 CASH trade。这是刻意设计——事件是被动发生的公司行为，不是主动交易。

### 1.3 transfer_group 命名规则

```
sub_{subscription.id}     → 申赎派生的单条 CASH trade
rebal_{uuid12}            → 基金调仓的基金腿 + CASH 腿配对（2条）
{uuid12} (无前缀)          → 跨平台现金转移的两条 CASH trade（2条）
```

唯一约束（`trade.py:34`）：`UniqueConstraint('transfer_group', 'product_code', 'trade_type')`，防止重复确认生成重复 CASH trade。

## 2. 交易处理三大模块

### 2.1 Subscription（申购/赎回）

#### 2.1.1 数据模型

```
Subscription
├── sub_type: subscribe(申购) / redeem(赎回)
├── amount: 申购时输入金额，赎回时确认后计算
├── shares: 赎回时输入份额，申购时确认后计算
├── unit_price: 确认时从组合快照取净值
├── apply_date: 申请日（交易日）
├── confirm_date: 确认日 = T+1（固定，不读 product.confirm_days）
├── status: pending → confirmed / cancelled
├── platform_code: 必填（追踪现金归属平台）
└── investor_code: 投资人
```

#### 2.1.2 完整流程

**创建（pending）**：
1. 交易日校验 → 2. 组合校验（active 或 draft）→ 3. 快照日期校验（apply_date > latest_snapshot_date）→ 4. 平台/投资人校验 → 5. 申购校验 amount > 0 / 赎回校验 shares ≤ 可用份额 → 6. 落库 status=pending

**确认（pending → confirmed）** — `subscription_service.py:41-153`：
1. 状态守卫（必须 pending）
2. 确认日 = `get_next_trading_day(apply_date, days=1)` — **固定 T+1**
3. 首次申购判断：同组合 confirmed subscribe 数为 0
4. **净值确定**（核心）：
   - 首次：`nav = 1.0000`（固定）
   - 非首次：取 **apply_date 当天** 的 `PortfolioValueSnapshot.unit_price`
   - 若 apply_date 无快照 → `NavNotAvailableError`
5. 份额/金额计算：
   - 申购：`shares = amount / nav`
   - 赎回：`amount = shares × nav`
6. 生成配对 CASH trade（`transfer_group = "sub_{id}"`）：
   - 申购 → CASH buy（现金增加）
   - 赎回 → CASH sell（现金减少）
   - **CASH trade 直接 confirmed**（不经 pending）
7. 首次申购激活组合（draft → active，started_at = confirm_date）
8. commit

**取消确认（confirmed → pending）** — `subscription_service.py:156-201`：
1. 快照保护：confirm_date 及之后已有快照 → 拒绝（`SNAPSHOT_DEPENDENCY`）
2. 回退字段：status=pending, confirm_date=None, unit_price=None, shares/amount=None
3. **物理删除配对 CASH trade**（`WHERE transfer_group = "sub_{id}"`）
4. commit

#### 2.1.3 可用份额实时计算（投资人维度）

```
投资人可用份额 = InvestorHolding.shares (最新快照)
              - SUM(pending 赎回 shares)                    // 全部扣减
              - SUM(confirmed 赎回 shares WHERE confirm_date > latest_snapshot_date)  // 快照未覆盖部分
```

> 位置：`position_service.py:220-271`，`subscriptions.py:36-85`（router 私有副本，逻辑一致）

### 2.2 Trade（调仓）

#### 2.2.1 数据模型

```
Trade
├── trade_type: buy / sell
├── product_code: 基金代码 或 "CASH"
├── market: CN_EXCHANGE(场内) / CN_OTC(场外) / ""(CASH)
├── amount: 买入=actual_amount-fee, 卖出=actual_amount+fee
├── shares: amount / price
├── price: 成交价
├── fee: 手续费
├── trade_date: 交易日
├── confirm_date: 创建时即根据 product.confirm_days 计算
├── transfer_group: rebal_{uuid} / sub_{id} / {uuid}
├── status: pending → confirmed / cancelled
└── platform_code: 平台
```

#### 2.2.2 完整流程

**创建（pending + 配对 CASH）** — `trades.py:229-397`：
1. 交易日校验 → 2. 组合校验（**必须 active**，不允许 draft）→ 3. 快照日期校验 → 4. 产品校验
2. **confirm_date 创建时即设定**：`expected_confirm_date = _get_next_trading_day(trade_date, days=product.confirm_days)`
3. 买入分支：
   - 校验 amount > 0
   - 校验可用现金：`calculate_available_cash(portfolio, platform)` ≥ amount
   - 计算：`amount = actual_amount - fee`, `shares = amount / price`
4. 卖出分支：
   - 校验 shares > 0
   - 校验可用份额：`_calculate_available_shares()` ≥ shares
   - 计算：`amount = actual_amount + fee`
5. **配对 CASH trade 生成**（仅当 product_code != "CASH"）：
   - `transfer_group = "rebal_{uuid12}"`
   - 基金买入 → CASH sell（现金减少）
   - 基金卖出 → CASH buy（现金增加）
   - CASH 腿与基金腿**同 pending、同 confirm_date、同 transfer_group**
6. commit（基金腿 + CASH 腿原子提交）

**确认（pending → confirmed）** — `trades.py:412-501`：
1. 状态守卫（必须 pending）
2. confirm_date 处理：接口传入则覆盖（补录场景），否则保留创建时设定值
3. 净值型产品净值获取（`_get_nav_for_trade_confirmation`）：
   - **QDII**：必须取 T 日净值，禁止向前查找 → `MISSING_QDII_NAV`
   - 非 QDII：取 T 日或最近交易日净值（`date <= trade_date` 倒序）
4. 重新计算交易数据（用最终价格重算 shares/amount）
5. `trade.status = "confirmed"` + **`_sync_transfer_group`** 同步配对 CASH 腿
6. commit

**`_sync_transfer_group` 原子同步机制** — `trades.py:113-137`：
```
查找同 transfer_group 且 id 不同的 trade → 同步 status 和 confirm_date
  - target_status == "confirmed": 配对腿 confirm_date = 基金腿 confirm_date
  - target_status == "pending": 配对腿重算 confirm_date（CASH 产品无 confirm_days，保持原值）
  - target_status == "cancelled": 配对腿同步 cancelled
```

**取消（pending → cancelled）** — `trades.py:504-530`：
- 场内交易不可取消（`CANNOT_CANCEL_EXCHANGE`）
- `_sync_transfer_group` 同步配对腿

**取消确认（confirmed → pending）** — `trades.py:533-561`：
- 重新计算 expected_confirm_date（基于 product.confirm_days）
- `_sync_transfer_group` 同步配对腿

#### 2.2.3 跨平台现金转移 — `cash_transfers.py`

复用 Trade 表，一次转移生成两条 CASH trade：

| 场景 | 卖出腿（转出平台） | 买入腿（转入平台） | confirm_date |
|------|-------------------|-------------------|---------------|
| 当天完成 (cross_day=False) | confirmed | confirmed | = transfer_date |
| 跨天到账 (cross_day=True) | pending | pending | = next_trading_day |

**对称状态设计**：跨天转移两腿均 pending → `compute_cash_balance` 不计入 → D 日 NAV 不虚跌。D+1 同时 confirm → 资金从 A 转移到 B。

### 2.3 ShareChangeEvent（份额变动事件）

#### 2.3.1 事件类型与分级

| 分级 | 类型 | 说明 | platform_code | 计算 |
|------|------|------|---------------|------|
| 基金级 | `share_split` | 份额拆分 | 禁止指定 | shares_after = es × ratio |
| 基金级 | `share_merge` | 份额合并 | 禁止指定 | shares_after = es / ratio |
| 基金级 | `bonus_share` | 送股 | 禁止指定 | shares_change = es × ratio |
| 平台级 | `cash_dividend` | 现金分红 | 必填 | cash_change = es × div_cash |
| 平台级 | `reinvest_dividend` | 红利再投 | 必填 | shares_change = es × div_cash / nav |
| 平台级 | `forced_adjustment` | 强制调整 | 必填 | 用户直接填写 |

**基金级事件**确认时自动拆分为各平台子记录（`parent_event_id = event.id`）。

#### 2.3.2 完整流程

**创建（pending）** — `share_change_events.py:160-257`：
1. 权益登记日 + 除息日校验（均须交易日，ex_date > entitlement_date）
2. 快照日期校验（ex_date > latest_snapshot_date）
3. 分级校验：平台级必填 platform_code，基金级禁止指定
4. 落库 status=pending（**创建时不计算 shares_change/cash_change**，确认时才算）

**确认（pending → confirmed）** — `share_change_events.py:272-337`：
1. 状态守卫（必须 pending）
2. **权益登记日持仓快照必须存在**（`PortfolioPosition.snapshot_date == entitlement_date`）→ 否则 `MISSING_POSITION_SNAPSHOT`
3. 基金级事件：查 entitlement_date 当天该产品所有平台持仓 → 为每平台创建子记录 → 父记录汇总
4. 平台级事件：查 entitlement_date 当天该产品该平台持仓 → `_compute_event_fields` 计算
5. commit

**取消（pending → cancelled）**：仅 pending → cancelled。

> **注意**：router 层**没有 unconfirm 接口**。confirmed 事件的回退只能通过删除快照时级联触发（`_cascade_unconfirm_share_change_events`）。

#### 2.3.3 事件对快照的影响

事件在快照生成时由 `_generate_portfolio_position` 应用（`snapshot_service.py:567-604`）：
- `cash_dividend` / `forced_adjustment`：`positions[cash_key]["amount"] += event.cash_change`（影响现金）
- 其他类型：`positions[fund_key]["shares"] += event.shares_change`（影响份额）
- **直接使用确认时预计算的 shares_change，不在快照生成时重算**

## 3. 快照生成模块

### 3.1 三表生成顺序与依赖

**固定顺序**：`portfolio_position` → `portfolio_value_snapshot` → `investor_holding`

```
_generate_portfolio_position(db, pf, date)
        │
        │ positions 作为内存参数传入
        ▼
_generate_portfolio_value_snapshot(db, pf, date, positions)
        │
        │ value_snapshot 作为内存参数传入
        ▼
_generate_investor_holding(db, pf, date, value_snapshot)
```

> 位置：`snapshot_service.py:63-95`（`generate_daily_snapshots` 函数）

| 快照表 | 依赖上游 | 依赖方式 |
|--------|---------|---------|
| portfolio_position | 前一日同表快照 + trade/event/manual_market_value/price_record | 增量法 |
| portfolio_value_snapshot | **同日 portfolio_position（内存传参）** + 前一日同表 + subscription | total_value = Σ(position 市值) |
| investor_holding | 前一日同表快照 + subscription | 份额增量累加 |

### 3.2 触发机制

**路径 A：定时任务**（`scheduler_service.py` → `task_runner.run_nav_sync`）
- Cron：`0 7 * * *`（每天 7 点）
- MySQL `GET_LOCK` 多 worker 互斥
- target_date = **today - 1**（处理昨天的快照）
- 流程：同步基金净值 → 分红检测 → 生成快照 → 自动确认 pending 申赎/事件

**路径 B：HTTP 手动**（`snapshots.py`）
- `POST /snapshots/generate` → `generate_daily_snapshots`
- `POST /snapshots/recalculate` → `recalculate_snapshots`

**路径 C：CLI**（`cli/commands/snapshots.py`）

### 3.3 前置依赖校验

`validate_snapshot_dependencies`（`snapshot_service.py:255-285`）包含 4 项：

| 检查项 | 规则 | 失败后果 |
|--------|------|---------|
| 交易日 | target_date 必须是交易日 | 阻断 |
| pending 交易 | Trade: `confirm_date <= target_date AND status=pending`；Subscription: `apply_date < target_date AND status=pending` | 阻断 |
| 净值完整性 | 所有持仓产品在 target_date 有可用净值 | 阻断 |
| 事件状态 | `ex_date <= target_date AND status=pending` | 阻断 |

> **注意**：Subscription 用严格小于 `< target_date`，意味着 apply_date == target_date 的 pending 申赎不阻止当日快照。这是因为申赎走 T+1 确认，apply_date=D 的申赎在 D 日快照生成时还是 pending，要等 D 日快照生成后由 `auto_confirm_after_snapshot` 自动确认。

### 3.4 各表生成逻辑

#### 3.4.1 portfolio_position（持仓快照）

`_generate_portfolio_position`（`snapshot_service.py:440-682`）采用**增量法**：

```
Step 1: 取前一日快照作为基准（key = product_code + market + platform_code）
Step 2: 应用窗口内 confirmed 买入 trade → 份额增加 + 加权平均成本
Step 3: 应用窗口内 confirmed 卖出 trade → 份额减少
Step 4: 应用窗口内 confirmed 事件 → shares_change / cash_change
Step 5: manual_market_value 绝对覆盖（CASH 持仓，日期精确匹配）
Step 6: 取价（QDII 用 T-1 净值，非 QDII 用 ≤ target_date 最新净值）
Step 7: 计算 frozen_shares（pending 卖出份额，按 trade_date）
```

**窗口范围**：`start_apply_date = prev_snapshot_date + 1`（首次无前序则 = target_date）

> **重要发现**：代码中 CASH 持仓实际上是在 `_generate_portfolio_position` 内部**增量累加**的（第510-516、553-558、576-582行），而非 AGENTS.md 所述"由 get_cash_value → compute_cash_balance 统一计算"。`compute_cash_balance` 用于实时预览，快照生成走增量累加路径。这是文档与代码的不一致。

#### 3.4.2 portfolio_value_snapshot（组合价值快照）

`_generate_portfolio_value_snapshot`（`snapshot_service.py:685-760`）：

```
total_value = Σ(position.market_value) + Σ(position.amount)
total_shares = 前一日快照 total_shares
             + SUM(confirmed 申购 shares WHERE confirm_date IN [prev+1, target])
             - SUM(confirmed 赎回 shares WHERE confirm_date IN [prev+1, target])
unit_price = total_value / total_shares  (保留4位小数)
frozen_shares = SUM(pending 赎回 shares WHERE apply_date <= target_date)
```

首次快照特殊处理：`total_shares = total_value`（NAV = 1.0）。

> **遗留问题**：`unit_price_change_pct` 字段存在但未填值。

#### 3.4.3 investor_holding（投资人持有快照）

`_generate_investor_holding`（`snapshot_service.py:763-862`）：

```
投资人份额 = 前一日快照 shares
           + SUM(confirmed 申购 shares WHERE confirm_date IN [prev+1, target])
           - SUM(confirmed 赎回 shares WHERE confirm_date IN [prev+1, target])
cost_per_share = 加权平均成本（申购时按 sub.unit_price）
frozen_shares = SUM(pending 赎回 shares WHERE apply_date <= target_date)
```

> **重要发现**：函数签名接收 `value_snapshot` 参数，但函数体内**未读取其任何字段**。`InvestorHolding` 表未持久化市值和收益字段，需调用方实时计算（shares × unit_price）。

### 3.5 快照不可变性保证

| 层级 | 机制 | 位置 |
|------|------|------|
| HTTP API | POST/PUT/DELETE 全部返回 422 | `positions.py:122-180` |
| 唯一约束 | 同组合同日同产品不重复 | 各 model 文件 |
| 生成前清理 | 生成前先删当日已有快照 | `snapshot_service.py:61` |

> **风险**：ORM 层未添加 SQLAlchemy event listener，内部代码 `db.query(PortfolioPosition).update()` 技术上可行。

## 4. 核心业务流程

### 4.1 新增数据录入流程

```
用户录入交易/事件
    │
    ├─ 交易日校验（trading_calendar.is_open）
    ├─ 快照日期校验（操作日 > latest_snapshot_date）
    ├─ 可用性校验（可用份额/可用现金）
    │
    ▼
落库（status=pending）
    │
    ├─ trade: 基金腿 + 配对 CASH 腿同 pending
    ├─ subscription: 仅 subscription 表，无 CASH trade
    ├─ event: 仅 event 表，无 CASH trade
    │
    ▼
人工确认 或 等待自动确认
    │
    ├─ trade confirm: 重算交易数据 + _sync_transfer_group 同步 CASH 腿
    ├─ subscription confirm: 取 apply_date 净值 + 派生 CASH trade(直接confirmed)
    ├─ event confirm: 从持仓快照取 entitlement_shares + 计算变动字段
    │
    ▼
等待快照生成（定时任务或手动）
    │
    ├─ 前置校验（无 pending 阻断快照的交易）
    ├─ 生成 portfolio_position（增量累加 trade + event）
    ├─ 生成 portfolio_value_snapshot（总市值 / 总份额 = 净值）
    ├─ 生成 investor_holding（投资人份额增量累加）
    │
    ▼
auto_confirm_after_snapshot（自动确认）
    │
    ├─ 确认 apply_date <= snapshot_date 的 pending 申赎
    ├─ 确认 confirm_date == snapshot_date 的 pending trade
    ├─ 确认跨天转移配对（两腿同时 confirmed）
    ├─ 确认 ex_date == snapshot_date 的 pending event
    │
    ▼
后续日期快照依赖当日快照（级联效应）
```

### 4.2 历史数据补录流程

补录的核心原则：**补录日当天及之后的快照必须删除后重建**。

```
用户发现需要补录历史数据（如 D 日的交易遗漏）
    │
    ▼
方式 A：调用 recalculate_snapshots(start_date=D, end_date=D)
    │
    │  ┌─ 自动检测：end_date 之后是否有快照
    │  │  → 若有，自动扩展 effective_end_date = latest_snapshot_date
    │  │  （因为 D 日快照重算后，D+1 依赖 D，必须级联重算）
    │  │
    │  ├─ 逐日循环（D → effective_end_date）：
    │  │   │
    │  │   ├─ 跳过非交易日
    │  │   ├─ 校验依赖（非 force 模式）
    │  │   │
    │  │   ├─ _delete_existing_snapshots(D)
    │  │   │   │
    │  │   │   ├─ _cascade_unconfirm_subscriptions
    │  │   │   │   → apply_date == D 的 confirmed 申赎 → 回退 pending
    │  │   │   │   → 物理删除 sub_{id} 的 CASH trade
    │  │   │   │
    │  │   │   ├─ _cascade_unconfirm_share_change_events
    │  │   │   │   → ex_date == D 或 entitlement_date == D 的 confirmed 事件
    │  │   │   │   → 物理删除子记录 + 父记录回退 pending
    │  │   │   │
    │  │   │   ├─ DELETE portfolio_position WHERE snapshot_date == D
    │  │   │   ├─ DELETE portfolio_value_snapshot WHERE snapshot_date == D
    │  │   │   └─ DELETE investor_holding WHERE snapshot_date == D
    │  │   │
    │  │   ├─ generate_daily_snapshots(D) — 重新生成三张表
    │  │   ├─ auto_confirm_after_snapshot(D) — 重新自动确认
    │  │   └─ commit（有条件，见 §5.2 问题）
    │  │
    │  └─ 返回结果
    │
    ▼
方式 B：手动两步操作
    │
    ├─ Step 1: DELETE /snapshots/{portfolio}/bulk/{from_date}
    │   → 按 snapshot_date DESC 逐日删除（含 from_date）
    │   → 每日触发级联回退
    │   → 最后统一 commit
    │
    ├─ Step 2: 录入新的历史数据（trade/subscription/event）
    │
    └─ Step 3: POST /snapshots/generate 逐日重新生成
```

#### 4.2.1 删除范围边界

| 操作 | 删除条件 | 含 from_date 当天 |
|------|---------|------------------|
| 单日删除 | `snapshot_date == target_date` | — |
| 批量删除 | `snapshot_date >= from_date` | **是** |
| 重算删除 | `snapshot_date == current_date`（逐日） | **是**（逐日处理） |

#### 4.2.2 级联回退机制

删除快照时的级联回退是保证数据一致性的关键：

**Subscription 级联回退**（`snapshot_service.py:310-354`）：
```
条件：apply_date == snapshot_date AND status == "confirmed"
动作：
  1. 调 unconfirm_single_subscription → 回退 pending
  2. 物理删除 transfer_group = "sub_{id}" 的 CASH trade
```

**Event 级联回退**（`snapshot_service.py:357-398`）：
```
条件：status == "confirmed" AND parent_event_id IS NULL
      AND (ex_date == snapshot_date OR entitlement_date == snapshot_date)
动作：
  1. 物理删除所有子记录（parent_event_id == event.id）
  2. 父记录回退 pending，清空 shares_change/cash_change/shares_after
```

**Trade 无级联回退**：删除快照不会回退 confirmed trade。因为 trade 的确认依赖 PriceRecord（产品净值），不依赖组合快照 NAV。

> **设计含义**：补录时如果 trade 数据本身有误（如 price 错误），需要手动 unconfirm → 修改 → 重新 confirm，删快照不会自动回退 trade。

## 5. 事务一致性分析

### 5.1 当前事务模型

系统统一使用 `SessionLocal = sessionmaker(autocommit=False, autoflush=False)`（`database.py:32`），**没有显式 `with db.begin()` 事务块**，依赖：
- 每个 `db.commit()` 作为一个事务边界
- 异常时不 commit → 自动回滚
- 部分代码显式 `db.rollback()`（如 `snapshot_service.py:115`）

| 操作 | 事务边界 | 原子性保证 |
|------|---------|-----------|
| trade create | 单个 commit | 基金腿 + CASH 腿原子 |
| trade confirm | 单个 commit | 基金腿 + _sync_transfer_group 原子 |
| subscription confirm | 单个 commit | subscription + CASH trade + portfolio 状态原子 |
| subscription unconfirm | 单个 commit | subscription 回退 + CASH trade 删除原子 |
| event confirm（基金级） | 单个 commit | 父记录 + 所有子记录原子 |
| 快照生成（单组合单日） | 单个 commit | 三张表原子 |
| 快照批量删除 | 最后统一 commit | 所有日期原子 |
| 快照重算（逐日） | **每日独立 try/except** | 单日失败不影响其他日 |

### 5.2 发现的问题

#### 问题 1：recalculate_snapshots 中的条件性 commit（严重）

`snapshot_service.py:222-227`：
```python
auto_results = auto_confirm_after_snapshot(db, portfolio.code, current_date)
if auto_results:          # ← 只有非空才 commit
    db.commit()
    result["auto_confirmed"].extend(auto_results)
```

**问题**：如果某天没有需要自动确认的 pending 申赎/事件，`auto_results` 为空列表，`if []:` 为 False，**不会 commit**。当天生成的快照留在 session 中未持久化。

**后果**：
- 后续日期的 `_delete_existing_snapshots` 在同一 session 内能"看到"未 commit 的数据，可能正常工作
- 但如果循环中途某天异常 → `db.rollback()` → **之前所有未 commit 的快照全部丢失**
- 对比 `task_runner._generate_snapshots_for_date` 是**无条件** commit（正确做法）

#### 问题 2：CASH 计算双路径（manual 边界正确，注释需修正）

存在两套 CASH 余额计算路径，区别在于计算方式（增量累加 vs 全量重算）和 `manual_market_value` 的使用时机：

| 路径 | 函数 | 用于 | 实现方式 | 查 manual? |
|------|------|------|---------|-----------|
| 增量法 | `_generate_portfolio_position` 内部累加 | 快照落库（日终） | 前日快照 + 窗口内 trade/event | ✅ 查 `target_date`（日终） |
| 显式重算 | `compute_cash_balance` | 审计字段 | trade CASH + event cash_change 全量重算 | ❌ 不查 |
| 含 manual | `get_cash_value` → `calculate_available_cash` | 实时可用现金 | compute_cash_balance + manual 绝对替换 | ✅ 查 `latest_date`（过去日终） |

**manual 使用边界验证**（符合"日终值不能用于日中实时"原则）：
- 快照生成：查 `target_date`（日终）的 manual → ✅ 正确
- 实时可用现金 `calculate_available_cash`：基线查 `latest_date`（最新快照日 = 过去日终）的 manual，不查 today → ✅ 正确
- 审计字段 `compute_cash_balance(update_date)`：不查 manual → ✅ 正确
- 没有端点调 `get_cash_value(today)` 做实时预览 → ✅ 不会误用 today 的 manual

**唯一问题**：`compute_cash_balance` 注释（`position_service.py:32`）声称"实时预览和快照生成均调用此函数"，但实际快照生成走增量累加路径未调用此函数。注释与代码不一致，已提 Issue #28 修正。

> 结论：双路径的 manual 使用边界正确，非数据风险。两条路径在数据一致时理论上等价，区别仅在于增量法依赖前日快照基准（如有 bug 会传播），显式重算法独立计算不受基准影响。统一为单一路径是代码简化建议（见建议 4），非数据安全修复。

#### 问题 3：并发安全缺失

- 无 `SELECT ... FOR UPDATE` 行锁
- 状态守卫是应用层检查（如 `if trade.status != "pending"`），非数据库层
- 并发确认同一 subscription/trade 时存在竞态条件
- 项目实际是单 admin 操作场景，风险可控但不严谨

#### 问题 4：Trade 无级联回退机制（设计正确，非缺陷）

删除快照时：
- Subscription → 级联回退（含 CASH trade）
- Event → 级联回退（含子记录）
- **Trade → 不回退**（正确设计）

trade 不回退是因为其 confirm 依赖 `PriceRecord`（产品净值），不依赖组合快照。删快照不影响 trade 数据有效性。如果 trade 的 price/shares 数据有误，应由用户手动 `unconfirm → 修改 → confirm` 修正，而非通过删快照触发。详见建议 8 的分析。

#### 问题 5：Router 与 Service 代码重复

- `subscriptions.py:36-85` 的 `_calculate_investor_available_shares` 与 `position_service.py:220-271` 逻辑完全一致
- `trades.py:157-205` 的 `_calculate_available_shares` 与 `position_service.py:169-217` 一致
- 维护时两处都要改，容易遗漏

#### 问题 6：Event 无 unconfirm 接口

router 层没有 `/{id}/unconfirm` 端点。confirmed 事件的回退只能通过删除快照级联触发。如果需要在不删快照的情况下回退 confirmed 事件，没有 API 支持。

#### 问题 7：批量删除的事务粒度过大

`delete_snapshots_bulk`（`snapshots.py:205-277`）：
- 逐日删除 + 级联回退，但**最后统一 commit**（第270行）
- 如果删除第 100 天时失败 → `db.rollback()` → 前 99 天的删除和级联回退全部回滚
- 大范围补录时事务过大，锁持有时间长

## 6. 优化建议

### 6.1 事务一致性改进

#### 建议 1：修复 recalculate_snapshots 的条件性 commit（P0 紧急）

```python
# snapshot_service.py recalculate_snapshots 内
# 修改前：
auto_results = auto_confirm_after_snapshot(db, portfolio.code, current_date)
if auto_results:
    db.commit()

# 修改后（对齐 task_runner 的做法）：
auto_results = auto_confirm_after_snapshot(db, portfolio.code, current_date)
db.commit()  # 无条件 commit，保证每日快照独立持久化
if auto_results:
    result["auto_confirmed"].extend(auto_results)
```

#### 建议 2：引入显式事务块

对跨表原子操作使用 `with db.begin()` 子事务，确保异常时精确回滚：

```python
# 示例：trade confirm
def confirm_trade(trade_id, ...):
    with db.begin_nested():  # savepoint
        trade = db.query(Trade).filter(Trade.id == trade_id).with_for_update().first()
        if trade.status != "pending":
            raise InvalidStatusError(...)
        # ... 计算逻辑 ...
        _sync_transfer_group(db, trade, "confirmed", trade.confirm_date)
    # 离开 with 块自动 commit savepoint
```

#### 建议 3：并发安全 — 关键操作加行锁

对 confirm/unconfirm 操作使用 `SELECT ... FOR UPDATE`：
```python
trade = db.query(Trade).filter(
    Trade.id == trade_id
).with_for_update().first()  # 加行锁
```

### 6.2 边界划分改进

#### 建议 4：统一 CASH 计算路径（代码简化）

快照生成中的 CASH 持仓可改为调用 `get_cash_value()`，消除增量累加路径：

```python
# _generate_portfolio_position 中 CASH 处理改为：
for platform in active_platforms:
    cash_amount = get_cash_value(db, portfolio_code, platform.code, target_date)
    positions[("CASH", "", platform.code)] = {
        "shares": None,
        "amount": cash_amount,
        "asset_type": "cash",
    }
# 删除原来的 trade CASH 累加 + event cash_change 累加 + manual 覆盖逻辑
```

好处：单一数据源，代码更简洁。经分析双路径的 manual 使用边界已正确（见问题 2 验证），此为代码可维护性优化而非数据安全修复。需验证性能（全量重算 vs 增量累加）。

#### 建议 5：消除 Router/Service 代码重复

将 `subscriptions.py` 和 `trades.py` 中的私有计算函数全部改为调用 `position_service` 的公共版本，删除 router 内的副本。

#### 建议 6：为 Event 增加 unconfirm 接口

```python
@router.post("/{event_id}/unconfirm")
def unconfirm_event(event_id, ...):
    # 1. 快照保护：ex_date 之后有快照 → 拒绝
    # 2. 父记录回退 pending + 清空计算字段
    # 3. 物理删除子记录
    # 4. commit
```

### 6.3 快照重建逻辑改进

#### 建议 7：批量删除改为逐日 commit

```python
# snapshots.py delete_snapshots_bulk 修改：
for snap_date in snapshot_dates:
    try:
        result = _delete_existing_snapshots(db, portfolio_code, snap_date)
        db.commit()  # 每日独立 commit，避免大事务
        results.append(...)
    except Exception as e:
        db.rollback()
        raise HTTPException(...)
```

好处：降低锁持有时间，失败时已删除的日期不会回滚。

#### 建议 8：Trade 不级联回退（确认现有设计正确）

经分析，trade **不需要**级联回退，应保持现有设计。原因在于三个模块对快照的依赖不同：

| 模块 | confirm 时取什么数据 | 删快照后数据是否有效 | 需要回退? |
|------|---------------------|-------------------|----------|
| subscription | 组合快照 `unit_price`（NAV） | ❌ NAV 没了 → unit_price 失效 | ✅ 必须 |
| event | 持仓快照 `entitlement_shares` | ❌ 持仓数据没了 → shares_change 失效 | ✅ 必须 |
| trade | `PriceRecord` 产品净值 | ✅ 不受快照影响 → 数据仍有效 | ❌ 不需要 |

**subscription/event 必须回退**：它们的确认依赖快照数据（NAV / 持仓份额），删快照后这些数据源消失，confirmed 状态下的 unit_price/shares_change 失效，必须回退 pending 等新快照生成后用新数据重新确认。

**trade 不需要回退**：trade 的 confirm 依赖 `PriceRecord`（产品净值表），与组合快照无关。删快照不影响 PriceRecord，trade 的 shares/amount/price 数据仍然有效。重新生成快照时直接用 confirmed trade 数据累加即可。

**正确流程（保持现有设计）**：
1. 删快照 → 级联回退 subscription + event（trade 保持 confirmed）
2. 用户检查/修正有误的 trade（如有）：`unconfirm → PUT 修改 → confirm`
3. 重新生成快照 → 用 confirmed trade 数据累加

**效率优势**：补录场景（大多数）只涉及加新数据，已有 confirmed trade 正确，不需要全部回退重新确认。仅在 trade 数据本身有误时，用户针对性 unconfirm 特定 trade。若级联回退所有 trade，会导致全部需要重新确认，操作代价过高。

> 结论：现有"trade 不级联回退"的设计是正确的，不应改变。我此前在此处提出的"可选级联回退"建议经进一步分析后撤回。

#### 建议 9：重算时先 unconfirm 后删快照的顺序保证

当前 `_delete_existing_snapshots` 内部先级联回退再删除快照，顺序正确。但建议增加日志记录级联回退的详情，便于审计和排查：

```python
logger.info(
    f"级联回退: portfolio={portfolio_code}, date={target_date}, "
    f"subscriptions={len(cascaded_subs)}, events={len(cascaded_events)}"
)
```

### 6.4 其他改进

#### 建议 10：补全遗留字段

- `PortfolioValueSnapshot.unit_price_change_pct`：计算 `(unit_price - prev_unit_price) / prev_unit_price`
- `InvestorHolding` 增加市值和收益字段（持久化，避免实时计算）

#### 建议 11：增加 SQLAlchemy event listener 兜底
