# 份额精度全局改为 2 位小数

## Summary

公募基金行业惯例：净值 4 位小数、投资人确认份额 2 位小数。当前系统份额字段为 `Numeric(15,4)` 且计算不量化，产生 6837.2967 这类虚构精度，导致用户按平台真实份额 6837.30 卖出时被零容差校验拒绝。项目处于开发测试阶段、历史数据可舍入，故采用全局精度变更方案：份额字段改 `Numeric(15,2)` + 所有份额产生点显式 quantize。

## 关键决策（实施者不得偏离）

1. **改动范围仅限份额字段**：金额类字段（`amount`/`actual_amount`/`fee`/`market_value`/`cash_change`/`total_value` 等）保持 `Numeric(15,4)`；净值/价格类字段（`unit_price`/`price`/`cost_per_share`/`ratio`）保持 `Numeric(10,4)` 不变。
2. **舍入模式统一 `ROUND_DOWN`**（第 3 位舍去，行业申购确认惯例），通过共享工具函数实现，禁止在各处散落写死舍入模式。
3. **不引入卖出容差**：源头量化后账本与平台一致，`INSUFFICIENT_SHARES` 校验保持精确比较不变；但卖出/赎回的**用户输入份额**需先量化到 2 位再校验（防止输入 6837.305 通过校验后被数据库舍成 6837.31 超出可用份额）。
4. **前端本次不改动**。
5. **迁移为单向**：downgrade 仅恢复列类型为 (15,4)，不恢复精度数据。

## 共享量化工具

新建 `backend/app/utils/quantize.py`：
- 常量 `SHARES_QUANT = Decimal("0.01")`。
- `quantize_shares(value: Optional[Decimal]) -> Optional[Decimal]`：None 原样返回，否则 `Decimal(str(value)).quantize(Decimal("0.01"), rounding=ROUND_DOWN)`，附 docstring 说明行业规范依据。

## Alembic 迁移

新建 `backend/alembic/versions/0004_shares_precision_2_digits.py`（revision `0004`，down_revision `0003`，风格参照 [0003_trade_transfer_group_not_null.py](file:///home/collyn/projects/InvestRing/backend/alembic/versions/0003_trade_transfer_group_not_null.py) 的防御性 try/except 写法）：
1. 先对上述 11 列执行 `UPDATE <table> SET <col> = ROUND(<col>, 2) WHERE <col> IS NOT NULL`（MySQL/SQLite 通用，保证数据舍入确定性，不依赖 ALTER 隐式行为）。
2. 再逐列 `op.alter_column(..., existing_type=sa.Numeric(15,4), type_=sa.Numeric(15,2))`，保持各列原有 nullable/default；SQLite 下 alter 失败时 try/except 容忍（SQLite 不强制 Numeric 精度，UPDATE 舍入已生效）。
3. downgrade：仅将列类型改回 (15,4)，注释说明精度数据不可恢复。
4. **与 issue #66 的关系**：#66（金额/日期字段命名治理）与本迁移表级相邻但列级零重叠（#66 针对 `amount`/`market_value`/`total_value`/`date` 的改名且 DB 迁移尚在评估，本迁移针对份额列改精度），**不合并**；在 0004 的 docstring 中注明「不涉及 #66 命名治理，#66 若做 DB 重命名另开迁移（如 0005）」。

## Rejected Alternatives

- **卖出/赎回加 ≤0.01 容差清仓**：治标不治本，用户输入份额 ≠ 实际成交份额破坏审计一致性；源头量化后无必要。
- **仅前端显示层舍入到 2 位**：账实仍不一致，尾差持续累积。
- **金额字段同步改 2 位**：金额是资金流精度口径，与本问题无关，扩大改动面且涉及费率计算余量，单独需求再议。
- **依赖数据库隐式舍入（不加显式 quantize）**：SQLite 测试环境不强制 Numeric 精度，隐式行为在测试中不可验证且 MySQL 默认 HALF_UP 与行业 ROUND_DOWN 不符。
- **与 issue #66 合并为一个 migration**：#66 是命名治理（列重命名 + 全链路契约调整），其 DB 迁移尚处「评估后再决定」阶段、无定稿列名清单；与精度变更（含不可逆数据舍入）性质与风险完全不同，合并会导致审阅难归因、回滚粒度变粗，且为等待 #66 定稿而阻塞本次交易痛点修复。项目未上线、无停机窗口约束，「同表少几次 ALTER」的收益可忽略。

## Assumptions

- 生产未上线，现有数据均为测试数据，迁移就地舍入可接受、不可逆。
- 生产目标库为 MySQL，测试环境为 SQLite（精度不强制，故靠显式 quantize + 单测保证行为）。
- 迁移后存量各表间可能存在分币级尾差（各列独立舍入所致），测试数据可接受，可用快照重算消除。
