# Issue #65 评估意见与实现计划：交易确认前预览

## 评估结论

**采纳需求，但不采纳 issue 作者推荐的方案 a（纯客户端复算），改为方案 c（后端 preview 端点）+ ir-cli 薄封装命令。**

### 需求本身：合理且有真实痛点
- 已核实 [confirm_single_trade](file:///home/collyn/projects/InvestRing/backend/app/services/trade_service.py#L147-L244)：pending 交易 `price=null`，确认时当场取 T 日净值重算并由 router 直接 `db.commit()`，确实无任何 dry-run 路径；issue 描述的"确认前无法核对净值/金额"完全属实，且已造成过实际取错日期的事故。

### 为何否决方案 a（纯客户端复算）
1. **违反项目核心架构原则**：AGENTS.md §4.1 明确"业务逻辑单一实现于 service，REST 与 CLI 共用，杜绝并行实现漂移"。方案 a 要求在 ir-cli 复制约 100 行确认计算逻辑（OTC 净值型判定、买卖公式、QDII、PRICE_NAV_MISMATCH 精度口径、CASH 腿镜像），是典型的并行实现。
2. **漂移风险有实证**：近期任务记录显示确认取价逻辑已连续重构多次（QDII 统一取 T 日净值、价格从"覆盖"改为"一致性校验"、CASH 腿金额同步修复）。若当时存在客户端复算版本，每次都会漂移出错。
3. **验收标准无法刚性保证**：issue 验收要求 preview 输出与 confirm **完全一致**。客户端用 float 复算 vs 后端 Decimal(quantize 0.0001) 计算，精度口径都难以严格对齐；唯一可靠方式是共用同一代码路径。
4. **"无需部署"的前提不成立**：已核实 [deploy.yml](file:///home/collyn/projects/InvestRing/.github/workflows/deploy.yml)——main 分支 CI 通过后自动构建镜像、SSH 部署、健康检查失败自动回滚。后端改动的部署成本仅是一次 merge，issue 作者高估了方案 c 的部署代价。
5. 方案 a 还需绕过 #60 缺陷（±2 天窗口查净值再本地筛选 T 日），引入额外脆弱性；方案 c 后端直接精确查 T 日 `price_record`，#60 与本需求解耦。

### 为何否决方案 b（--dry-run 客户端标志）
本质仍是客户端复算（与 a 同样的漂移问题），且 `--dry-run` 语义容易与"真实提交"混淆，误操作风险高于独立的 `preview` 子命令。

### 方案 c 的可行性已验证
- Service 层约定"不 commit（可 flush）"（有 [test_service_no_commit.py](file:///home/collyn/projects/InvestRing/backend/tests/unit/test_service_no_commit.py) 强制），preview 端点天然支持"只算不落库"。
- 但注意：`confirm_single_trade` 会**原地修改 trade 对象**并在 `sync_transfer_group` 内做 savepoint flush，直接调用后靠"不 commit"回滚虽可行但不干净。正确做法是**提取纯计算函数**（见下）。

## 实现计划

### 后端改动

**1. 提取纯计算函数**（[trade_service.py](file:///home/collyn/projects/InvestRing/backend/app/services/trade_service.py)）
- 新增 `calculate_confirm_preview(db, trade, product, *, confirm_date=None, price=None) -> dict`：
  - 复用现有 L181-233 的计算分支逻辑，但**不修改 trade 对象、不调 sync_transfer_group**，只返回计算结果字典：`{price, shares, amount, actual_amount, fee, confirm_date, nav_date, is_otc_nav_fund, paired_cash_amount}`。
  - OTC 净值型：调 `get_nav_for_trade_confirmation` 取 T 日净值，缺失照常抛 `MISSING_NAV`（与 confirm 行为一致，让用户提前发现净值未同步）；传入 price 时执行同样的 `PRICE_NAV_MISMATCH` 校验。
  - 场内/非净值型：不传 price 时直接返回 trade 现有字段（confirm 不重算）；传 price 时按覆盖价重算。
  - `paired_cash_amount` = 基金腿 actual_amount（与 `sync_transfer_group` 镜像规则一致）。
- 重构 `confirm_single_trade`：调用 `calculate_confirm_preview` 获取结果后回写 trade 字段 + 置 confirmed + sync_transfer_group。**保证两条路径共用同一计算实现**（这是验收标准的根本保障）。

**2. 新增 preview 端点**（[routers/trades.py](file:///home/collyn/projects/InvestRing/backend/app/routers/trades.py)）
- `GET /api/trades/{id}/preview?confirm_date=&price=`，权限与 confirm 一致（`get_current_admin`），但为只读语义、**不调用 db.commit()**：
  - 校验 trade 存在且 `status == "pending"`（否则 422 `INVALID_STATUS`，与 confirm 端点口径一致）。
  - 查 product，调 `calculate_confirm_preview`，返回 `{trade: 现有字段, preview: 计算结果, paired_cash_leg: {...}}`。
  - `MISSING_NAV` / `PRICE_NAV_MISMATCH` 由全局 BusinessError handler 正常返回，preview 即可提前暴露 confirm 会遇到的错误——这本身就是预览的价值之一。
- 新增响应 schema（`app/schemas/trade.py`），字段名/类型明确（同时回应 #64 对响应契约的诉求）。

### ir-cli 改动

**3. 新增 `ir trade preview` 子命令**（[ir_cli/commands/trades.py](file:///home/collyn/projects/InvestRing/ir-cli/ir_cli/commands/trades.py)）
- 参数与 `confirm` 对齐：`id`（必填）、`--confirm-date`、`--price`、`--quiet`；仅做 `client.get(f"/api/trades/{id}/preview", params=...)` 薄封装，按 output.py 现有 `success(data=..., hints=[...])` 协议输出。
- hints 输出：`"核对无误后执行: ir trade confirm <id>"`。
- 在 [hints.py](file:///home/collyn/projects/InvestRing/ir-cli/ir_cli/hints.py) 补充 `MISSING_NAV` 提示（建议 `ir market sync` / 查询净值命令）。
- 同步更新 `backend/cli`（管理 CLI）的 trade 命令组：直连版 preview 调用同一 `calculate_confirm_preview`（两套 CLI 命令组保持一致，见 AGENTS.md §6）。

### 测试计划

**4. 一致性测试（验收核心）**（`backend/tests/integration/test_trades.py` 扩展）
- 场外 OEF/LOF 买入与卖出各一例：先 GET preview，再 POST confirm，断言 `shares/amount/actual_amount/price/confirm_date` 逐字段完全相等，且配对 CASH 腿金额 == preview 的 `paired_cash_amount`。
- QDII 产品（confirm_days=2）：preview 的 confirm_date 与 confirm 一致。
- 负例：T 日净值缺失 → preview 返回 `MISSING_NAV`；传入不一致价格 → `PRICE_NAV_MISMATCH`；非 pending → `INVALID_STATUS`。
- **副作用零断言**：preview 调用后 trade 仍为 pending、`price` 仍为 null、无新增/变更的 CASH 腿记录。
- 回归：现有 confirm 全量测试必须继续通过（重构 `confirm_single_trade` 后）；`test_service_no_commit.py` 覆盖新函数。

### 交付顺序与依赖
1. 后端提取计算函数 + 重构 confirm（先保证回归通过）→ 2. preview 端点 + schema → 3. 一致性/负例测试 → 4. 两套 CLI 的 preview 命令 → 5. 更新 `CLI_MANUAL.md` 与 AGENTS.md §4.2 路由表（+1 端点）。
- 部署：merge 到 main 后 CD 自动部署；ir-cli 侧命令可与后端同 PR 提交，但需在后端部署完成后才可用（可在命令 docstring 注明最低后端版本）。

## 风险与缓解
- **重构 confirm_single_trade 引入回归**：这是本方案最大风险。缓解：纯提取式重构（计算逻辑逐行搬移不改语义），依赖现有 679 行 test_trades.py 集成测试 + 新增一致性测试兜底。
- **preview 与 confirm 之间数据变化**（如净值补录、trade 被修改）：preview 是时点快照，在 CLI hints 中注明"实际以确认时为准"；由于共用代码路径，同等输入下结果必然一致。
- **GET 端点带业务异常语义**（422）：与项目现有约定一致（全局 handler 统一处理），无额外前端契约影响。

## Rejected Alternatives
- **方案 a（纯客户端复算，issue 作者推荐）**：违反 service 单一实现原则；确认逻辑近期多次重构证明漂移风险真实存在；float/Decimal 精度口径无法保证"完全一致"验收标准；还需为 #60 缺陷做 ±2 天窗口 workaround。其唯一优势"无需部署"在自动化 CD 面前不成立。
- **方案 b（confirm --dry-run）**：与 a 同样的复算漂移问题，且 dry-run 标志与真实提交仅一 flag 之差，误操作风险高。
- **直接调用 confirm_single_trade 后不 commit 实现 preview**：虽然 session 结束会回滚，但函数会原地改 trade 对象并在 savepoint 内 flush 配对腿，GET 端点携带写语义不干净，且 `db.refresh` 等细节易踩坑；提取纯计算函数更清晰且顺带消除 confirm 路径的重复代码。
- **扩展 TradeResponse 附带产品字段**（Alex 方案中的 Step 3a）：为方案 a 服务的改动，方案 c 下不需要；且已存在 `GET /api/products/{code}/{market}` 可单独取产品信息。
